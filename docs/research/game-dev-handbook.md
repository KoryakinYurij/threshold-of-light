## 1. Главная идея: разделяй слои (то, что вы помнили)

Вы правильно помните суть: **логика отдельно, графика отдельно, и «что-то ещё» отдельно**. В профессиональном геймдеве это называется **Separation of Concerns (разделение ответственностей)** и оформляется через слои.

Игра — это не один кусок кода, а **несколько независимых «слоёв»**, которые общаются между собой через узкие, заранее оговорённые «шлюзы» (интерфейсы/события):

| Слой | За что отвечает | Пример |
|------|-----------------|--------|
| 🧠 **Model / Domain (логика игры)** | Чистые правила игры, состояние, расчёты. **Не знает** ни о картинке, ни о звуке. | «Здоровье игрока = 50», «урон = атака − защита», «уровень пройден, когда собрано 10 кристаллов» |
| 🎨 **View / Render (графика)** | Только отображение: спрайты, анимации, камера. Читает состояние из Model, не меняет правила. | Нарисовать персонажа в позиции (x, y), проиграть анимацию прыжка |
| 🎮 **Input / Controller (ввод)** | Перевод нажатий клавиш/касаний в команды для Model. | Клавиша «Пробел» → команда `Jump()` |
| 🔊 **Audio (звук)** | Воспроизведение звуков/музыки. Реагирует на события, не содержит игровой логики. | По событию «враг убит» → играть звук взрыва |
| 💾 **Persistence (сохранение)** | Запись/чтение прогресса. Model не знает *как* сохраняем (файл, облако). | Сохранить состояние в JSON/файл сохранения |
| 🌐 **Networking (сеть)** — если нужно | Синхронизация между клиентами. | (на будущее, если будет мультиплеер) |

> 🎯 **Тест на хорошую архитектуру:** представьте, что вы удалили слой **графики** целиком. Игра должна продолжать «работать» в голове — враги двигаются, здоровье уменьшается, счёт растёт, просто без картинки. Если логика «живёт» внутри функций отрисовки — это плохая архитектура (её называют «спагетти»).

Это и есть тот «что-то ещё», который вы забыли: **звук, ввод, сохранение и (потом) сеть** — всё это отдельные слои, наравне с логикой и графикой.

**Почему это критично именно для вас (с ИИ):**
- Каждый слой можно тестировать **независимо** → меньше багов.
- Можно поменять графику на лучшую, **не трогая** логику.
- ИИ может разрабатывать слой за слоем, не путаясь → более чистый код.
- Если поменяется движок — основная логика (Model) переезжает почти без изменений.

## 2. Как новичку разрабатывать игру вместе с ИИ

### 2.1. Что реально может ИИ (состояние на 2026 г.)

✅ **Отлично справляется:**
- Быстрые прототипы, болванки (boilerplate), утилиты.
- Шейдеры, процедурная генерация, простые ИИ-поведенки.
- Генерация тестов, документации, рефакторинг.
- Объяснение незнакомых API, концепций, разбор ошибок.
- 2D-игры в браузере/движке — особенно пазлы, платформеры, карточные, аркады.

⚠️ **Слабо / требует вашего контроля (трактовать как «первый черновик»):**
- Сетевой код (netcode), точная синхронизация звука, система сохранений.
- Производительность, работа с памятью, потоками.
- Сложная 3D-физика и анимация.
- Когда проект перерастает **~10 000 строк** или появляются тесно связанные подсистемы — продуктивность ИИ может *падать* (данные METR/Faros). Тогда переводите его в роль «ревьюера/помощника», а не «главного автора».

🔑 Ключевой вывод индустрии: **«Инженер в цикле» (engineer-in-the-loop)**. ИИ ускоряет рутину, но понимание требований, архитектуры, безопасности и качества **остаётся вашей ответственностью**. Относитесь к коду ИИ как к черновику джуниора — всегда читайте, тестируйте, проверяйте.

### 2.2. Выбор движка определяет ~80% «потолка» ИИ

Движок стоит выбрать **до** глубокого старта. Для новичка с ИИ в 2026 г.:

| Движок | Язык | Кому подходит | ИИ-дружелюбность |
|--------|------|---------------|------------------|
| **Godot** | GDScript / C# | Бесплатный, лёгкий, отлично подходит для 2D/3D инди. Рекомендуется как старт по умолчанию для соло с ИИ. | ⭐⭐⭐⭐⭐ |
| **Браузер (Phaser / Three.js / Canvas)** | JavaScript / TypeScript | Самый быстрый старт, код в одном файле, мгновенный результат. | ⭐⭐⭐⭐⭐ |
| **Unity** | C# | Огромная экосистема, много туториалов, мобиль/инди. | ⭐⭐⭐⭐ |
| **Unreal** | C++ / Blueprints | ААА-графика. Сложнее для новичка и ИИ. | ⭐⭐ |

> Совет: для **первой** игры выберите то, где быстрее всего получите **играбельный** результат. Лучше закончить маленькую игру, чем бросить амбициозную.

### 2.3. Золотые правила работы с ИИ (на основе best practices 2026)

1. **«Архитектура — сначала».** Прежде чем кодить, попросите ИИ *объяснить архитектурные компромиссы и точки отказа*. Заставьте модель думать о дизайне, а не сразу писать код.
2. **Context packing (упаковка контекста).** Качество ответа резко растёт, когда ИИ видит структуру проекта, ограничения, соглашения, документацию API. Не заставляйте ИИ «летать вслепую» — прикладывайте релевантные файлы/документацию.
3. **Дробите задачи.** Не «сделай мне игру», а маленькие шаги: «сделай функцию X», «реализуй состояние Idle в FSM». Один шаг → проверка → следующий.
4. **«Сначала спека, потом код» (Spec-Driven Development).** Опишите задачу текстом/`TASK.md`, скормите ИИ, получите план, потом реализацию.
5. **Trust but verify (доверяй, но проверяй).** Прогоняйте код ИИ через линтер и тесты **до** того, как примете. Понимайте код достаточно, чтобы отвергнуть плохое предложение.
6. **Просите альтернативы.** Вместо одного решения просите 2–3 варианта с компромиссами — так ИИ честнее показывает выбор.
7. **Discipline of commits (коммит на каждое изменение).** Фиксируйте маленькие шаги в Git. Если ИИ сломал — легко откатиться. Это сохраняет «аудитируемость».
8. **Document early (документируйте рано).** README/AGENTS.md/тесты, написанные рано, делают последующие ответы ИИ точнее.
9. **Файлы контекста.** Заведите в корне `AGENTS.md` (стандарт) — см. раздел 13. Это «шпаргалка» проекта для любого ИИ-инструмента.

## 4. Карта необходимых навыков

Вам не нужно знать всё сразу. Вот **приоритезированная карта** — идите сверху вниз.

### 🥇 Уровень 1 — фундамент (без него никак)
- **Основы программирования:** переменные, условия, циклы, функции, массивы/списки, словари.
- **ООП (объектно-ориентированное программирование):** классы, объекты, наследование, инкапсуляция, полиморфизм, **композиция вместо наследования**.
- **Типы данных и структуры:** массив, список, множество (set), словарь (map), очередь, стек.
- **Работа в выбранном языке** (GDScript / C# / TS) — на базовом уровне.

### 🥈 Уровень 2 — геймдев-специфика
- **Игровой цикл (game loop):** update / render, `delta time`, фиксированный шаг для физики.
- **Конечные автоматы (FSM):** для состояний игрока/врагов/меню.
- **Компонентный подход / ECS:** как собирать объекты из «деталей».
- **События (events / observer):** как системы общаются без жёстких связей.
- **Ввод игрока:** обработка клавиш/мыши/тача, ремаппинг.
- **Сцены/уровни:** загрузка, переключение, меню.
- **Сохранение/загрузка** прогресса.

### 🥉 Уровень 3 — качество и масштаб
- **Тестирование:** unit-тесты, как писать тестируемый код.
- **Git и контроль версий** (раздел 11).
- **Чистый код и SOLID** (раздел 7).
- **Архитектура** (раздел 5) и паттерны (раздел 6).
- **Отладка (debugging):** читать ошибки, ставить точки останова, логировать.
- **Оптимизация** (только когда появляются проблемы!): object pooling, кэш локальности.

### 🎨 Уровень 4 — окрестные дисциплины (по мере роста)
- Гейм-дизайн: game feel, кривая сложности, плейтестинг, баланс.
- Базовая математика/физика: векторы, движение, столкновения.
- Работа с ассетами: спрайты, анимация (Aseprite, Blender), звук (Audacity).
- UI/UX: меню, HUD, отзывчивость интерфейса.
- (позже) сетевой код, экспорт/публикация, маркетинг.

### 🛠️ Софт-скиллы разработчика-соло
- **Управление скоупом (scope):** самая частая причина провала первой игры — завышенный размах. Делайте маленькое и доводите до конца.
- **Итеративность:** маленькие шаги + частая обратная связь.
- **Дисциплина рефакторинга:** «работает → потом чисто», но не оставляйте спагетти надолго.

## 5. Архитектура: Clean Architecture для игр

**Clean Architecture** (Роберт Мартин «дядя Боб») адаптируется под игры так: представьте **4 концентрических кольца**. Главное правило — **«Правило зависимостей»: зависимости всегда направлены внутрь.** Внешнее кольцо знает о внутреннем, внутреннее **никогда** не знает о внешнем.

```
        ┌─────────────────────────────────────────────┐
        │  4. Infrastructure / Engine (движок, файлы,  │  ← знает обо всём внутри
        │     сеть, рендер, аудио-движок)              │
        │  ┌───────────────────────────────────────┐  │
        │  │  3. Controllers / Adapters             │  │
        │  │     (перевод ввода/UI в вызовы логики) │  │
        │  │  ┌─────────────────────────────────┐  │  │
        │  │  │  2. Use Cases (сценарии)          │  │  │
        │  │  │     (SaveGame, StartLevel, ...)  │  │  │
        │  │  │  ┌───────────────────────────┐  │  │  │
        │  │  │  │  1. CORE / DOMAIN          │  │  │  │  ← никто снаружи не нужен
        │  │  │  │  (сущности, правила,       │  │  │  │     для компиляции/тестов
        │  │  │  │   чистое состояние игры)   │  │  │  │
        │  │  │  └───────────────────────────┘  │  │  │
        │  │  └─────────────────────────────────┘  │  │
        │  └───────────────────────────────────────┘  │
        └─────────────────────────────────────────────┘
```

### Что в каждом кольце

**1. Core / Domain (ядро) — самая ценная часть**
- Сущности и правила вашей игры: здоровье, инвентарь, формула урона, правила «порога света».
- Чистые данные и функции. **Никакого** движка, рендера, файлов, сети.
- Определяет **«порты»** — интерфейсы того, что ему нужно снаружи (например, `interface ISaveGame { save(state) }`). Реализация «порта» живёт снаружи.
- Если удалить все остальные кольца — ядро **всё равно компилируется и тестируется**. Это и есть мерило.

**2. Use Cases (сценарии)**
- Прикладная логика: `StartLevel`, `CollectCrystal`, `DefeatEnemy`, `SaveGame`. Оркестрируют ядро.

**3. Controllers / Adapters**
- Презентационная логика без движкового кода: перевод ввода и UI в вызовы Use Cases. Знают о ядре и о своих View (через интерфейсы).

**4. Infrastructure / Engine**
- Всё, что касается внешнего мира: сам движок, рендер, аудио-движок, файлы сохранений, сеть. **Зависит от всего внутри, но ничто внутри не зависит от него.** Здесь живут «адаптеры», реализующие порты ядра.

### Практический (не академический) подход для новичка-соло

Индустрия (Reddit r/ExperiencedDevs, r/gamedev) единодушна: **не переусложняйте**. Полная Clean Architecture на старте — это over-engineering. Реалистичная адаптация:

1. **Главное — держите логику (Model) чистой и отделённой от движка/рендера.** Это даёт 90% выгоды (тестируемость, переносимость, чистота) при 20% усилий.
2. **Не пытайтесь сделать логику «абсолютно независимой от движка»** ради гипотетического переезда на другой движок — это требует кучи слоёв абстракций, а переезд движка почти не случается. Делайте логику переносимой, но не фанатично.
3. **Сначала прототип → потом архитектура.** «Сначала работает, потом чисто, потом быстро». Не оптимизируйте и не абстрагируйте заранее (см. раздел 12).

> 🧩 **Когда чистая архитектура реально окупается:** проект живёт долго, сложная/сложно-меняемая логика, много систем, важна тестируемость. Для прототипа хватит простого разделения Model/View.

## 6. Паттерны проектирования (с примерами)

Главный источник — книга **Роберта Нистрома «Game Programming Patterns»** (бесплатно онлайн). Это «библия» геймдев-паттернов. Ниже — must-know для вас.

### 6.1. Game Loop (Игровой цикл) — сердце игры
Отвязывает прогресс игры от реального времени и скорости ввода.
```
пока игра идёт:
    processInput()      // собрать ввод
    update(deltaTime)   // шагнуть логику/физику
    render()            // нарисовать кадр
```
- **Физика** обычно на **фиксированном шаге** (fixed timestep) — стабильность; **рендер** — на переменном (`deltaTime`).
- Это «где живёт метод `update()`» — его вызывает цикл каждый кадр.

### 6.2. Update Method
Каждый объект (враг, снаряд) сам «тикает» себя раз в кадр. Позволяет симулировать множество независимых объектов.

### 6.3. Component (Компонент) — «композиция вместо наследования»
Собирайте объект из переиспользуемых компонентов, а не через глубокое наследование.
- `Hero = [Health, Movement, Sprite, Collider]`
- `Trap = [Damage, Sprite, Collider]`
- Каждый компонент отвечает за одну зону (рендер / физика / бой). Меняем поведение — меняем набор компонентов.

### 6.4. ECS (Entity-Component-System) — для множества объектов
- **Entity** = просто ID (без данных и логики).
- **Component** = чистые данные (Position, Health).
- **System** = логика, обрабатывающая все сущности с нужными компонентами (MovementSystem двигает всё, у чего есть Position + Velocity).
- Плюсы: дружелюбен к кэшу процессора (быстрый), огромная комбинаторика объектов (2ⁿ из n компонентов), лёгкое добавление фич.
- Используется в Unity DOTS, Bevy, Godot (частично). **Для первой игры можно начать с простого Component, а ECS — когда объектов реально много.**

### 6.5. State / FSM (Конечный автомат)
Меняет поведение объекта в зависимости от состояния. У каждого состояния методы `enter()`, `update()`, `exit()`.
- Игрок: `Idle → Run → Jump → Fall`.
- Враг: `Patrol → Chase → Attack`.
- Меню/игра: `MainMenu → Playing → Paused → GameOver`.
- **Контроль достигнутого чистого разделения:** состояние игры и врага должно жить в Model, а не в коде отрисовки.

### 6.6. Observer / Event Bus (События)
Системы реагируют на события без жёстких ссылок друг на друга (decoupling).
- Событие `"enemy_killed"` → UI обновляет счёт, Audio играет звук, Achievement-система проверяет ачивку.
- Реализуется через event bus / pub-sub. **Уменьшает связанность (coupling)** — то, что делает код тестируемым и модульным.

### 6.7. Command (Команда)
Действие упаковано в объект. Незаменимо для: **отмены (undo), повторов (replay), ремаппинга управления, ИИ** (ИИ «нажимает» те же команды, что игрок).

### 6.8. Object Pool (Пул объектов)
Переиспользуем объекты (пули, частицы, враги) вместо постоянного создания/удаления → избегаем фризов от сборщика мусора. **Не нужно на старте — включайте при тормозах.**

### 6.9. Service Locator / Dependency Injection — вместо Синглтона
- **Синглтон (Singleton)** — глобальный «менеджер всего». Удобен, но **часто анти-паттерн**: скрытое глобальное состояние, трудно тестировать, скрытые зависимости. Используйте **редко** (по-настоящему глобальные вещи типа доступа к железу).
- **Dependency Injection (внедрение зависимостей)** и **Service Locator** — предпочтительный способ: вы явно передаёте зависимости → код тестируется и меняется легко.

### 6.10. Type Object / Data-Driven (Данные вместо кода)
Определяйте новые «типы» объектов как **данные** (JSON/таблицы/ScriptableObject), а не как новые классы. Менять баланс/добавлять врагов — правите данные, код не трогаете. Это и есть **data-driven design** — одна из лучших практик для гейм-механик.

### Шпаргалка «когда применять»
| Задача | Паттерн |
|--------|---------|
| Двигать игру кадр за кадром | Game Loop + Update |
| Состояния игрока/врагов/UI | FSM (State) |
| Объекты из «деталей» | Component |
| Тысячи объектов быстро | ECS |
| Системы общаются без связей | Observer / Event Bus |
| Undo / replay / ремаппинг | Command |
| Много пуль/частиц без фризов | Object Pool |
| Баланс/новые враги без кода | Type Object / Data-driven |
| Глобальные сервисы тестируемо | DI / Service Locator (вместо Singleton) |

## 7. Принципы качественного кода (SOLID, DRY, KISS, YAGNI)

### SOLID — 5 принципов ООП (понимать на базовом уровне)
- **S — Single Responsibility (единственная ответственность):** один класс/модуль делает одну вещь. `Player` не должен сам сохранять игру и рисовать UI.
- **O — Open/Closed (открыт для расширения, закрыт для изменения):** новую функциональность добавляем, не ломая старую (через интерфейсы/компоненты).
- **L — Liskov Substitution:** подкласс можно использовать вместо базового без сюрпризов.
- **I — Interface Segregation:** много узких интерфейсов лучше одного «толстого».
- **D — Dependency Inversion:** зависим от абстракций (интерфейсов), а не от конкретных классов. Внутренние слои не зависят от внешних. *(Это и есть основа Clean Architecture.)*

### Принципы-аббревиатуры
- **DRY (Don’t Repeat Yourself):** повторяющийся код выносим в функцию. Копипаста = баги в нескольких местах.
- **KISS (Keep It Simple, Stupid):** простое решение лучше «умного». Преждевременная сложность — зло.
- **YAGNI (You Aren’t Gonna Need It):** не пишите фичи «авось пригодится». Реальный повтор → обобщение, не наоборот.

### Практические правила от ветеранов геймдева
- **Не используйте наследование только ради переиспользования кода.** Наследование — только при сильном отношении «является» (is-a), иначе — композиция.
- **Избегайте циклических зависимостей** (класс A зависит от B, а B от A).
- **Никаких синглтонов и глобального состояния** без веской причины — это	short-term решение за долгосрочную боль.
- **Рефакторинг — это нормально.** Не бойтесь переписать кусок, если стало грязно. Но «модульность и гранулярность» облегчат этот рефакторинг.
- **Избегайте преждевременной оптимизации.** «Сначала работает — потом быстро». Оптимизируйте **только** доказанное узкое место (после профилирования).

## 8. Тестируемость

Чистая архитектура существует во многом **ради тестов**. Для новичка тесты = страховка от того, что ИИ (или вы) что-то сломаете при изменениях.

### Уровни тестов
- **Unit-тесты (модульные):** проверяют чистую логику (Model) в изоляции. *Например: «формула урона при броне = атака/2». Легко, быстро, их много.*
- **Integration-тесты:** несколько систем вместе.
- **Ручной плейтест:** для гейм-фила и «фана» — автоматизировать нельзя, это ваша работа.

### Как писать тестируемый код (главное)
- Логика в **чистых функциях** (pure functions): вход → выход, без побочных эффектов. Их тестировать тривиально.
- Зависимости от движка/файлов/сети — через **интерфейсы** (порты). В тестах подменяйте их «заглушками» (mocks/stubs).
- Разделяйте **детерминированную логику** (правила) и **побочные эффекты** (рендер, звук, IO).

> ИИ отлично генерирует unit-тесты — поручайте ему это как рутину. Но **читайте** тесты: они фиксируют ожидаемое поведение.

## 9. Модульность и разделение систем

**Модульность** = система состоит из независимых, заменяемых блоков с чёткими границами. Это то, к чему вы стремились («логика отдельно, графика отдельно»).

### Признаки хорошей модульности
1. **Чёткие границы и интерфейсы** — модуль «договорился» с другими через узкий контракт.
2. **Низкая связанность (low coupling)** — модули мало знают друг о друге. Меняете один — другие не падают.
3. **Высокая связность (high cohesion)** — всё внутри модуля работает на одну цель.
4. **Замещаемость** — можно заменить модуль (графику, звук) не трогая остальные.
5. **Независимая тестируемость** — модуль проверяется сам по себе.

### «Тест на съёмность»
> Достигнуто хорошее разделение, если можно **вынуть** как можно больше компонентов и **остальные продолжат работать** независимо. (Например, убрали контроллер ввода — «доска»/мир всё ещё живёт и «рисуется»; контроллеры лишь дают ей подсказки.)

### Как общаются модули
- **События (event bus/observer)** — слабая связь, реактивность. По умолчанию.
- **Интерфейсы (порты/адаптеры)** — когда нужно вызывать конкретную возможность.
- **Dependency Injection** — для передачи зависимостей.
- **Прямые ссылки** — только между тесно связанными частями внутри одного модуля.

### Дополнительно к «логика/графика»: что ещё выносить отдельно
- **Audio** — отдельная система, подписанная на события.
- **Input** — отдельный слой; клавиша → команда (тогда легко менять управление и подключать ИИ-управление).
- **Save/Persistence** — через интерфейс; модель не знает формат хранения.
- **Configuration/Balance** — данные (JSON/таблицы), отдельно от кода (data-driven).

## 10. Структура проекта и папок

### Главное правило: группируйте по фиче, а не по типу
❌ Плохо (по типу): `scripts/`, `scenes/`, `sprites/`, `sounds/` — всё перемешано, сложно найти «всё про врага».
✅ Хорошо (по фиче): папка `enemy/` содержит `enemy.tscn`, `enemy.gd`, `enemy_sprites.png`, `growl.wav` — всё про врага вместе.

### Пример структуры (адаптируйте под движок)
```
threshold-of-light/
├── README.md                  # что это, как запустить
├── AGENTS.md                  # контекст для ИИ (раздел 13)
├── docs/
│   ├── PROJECT_CONTEXT.md     # живой снимок проекта (раздел 3)
│   ├── GAME_DESIGN.md         # гейм-дизайн-документ (сжатый)
│   └── ARCHITECTURE.md        # схема систем и связей
├── project/                   # сам проект движка (или src/ для веб)
│   ├── core/                  # 1. ЧИСТАЯ логика (без движка) — Model/Domain
│   │   ├── entities/          #   сущности, правила
│   │   ├── systems/           #   use cases / игровая логика
│   │   └── events/            #   определения событий/порты
│   ├── game/                  # 2-3. Сценарии + контроллеры
│   ├── ui/                    #    View: меню, HUD
│   ├── rendering/             #    View: рендер/спрайты/анимации
│   ├── audio/                 #    Audio-система
│   ├── input/                 #    Input-слой → команды
│   ├── persistence/           #    Save/Load (адаптеры портов)
│   └── assets/                #    картинки, звуки (группировать по фиче)
├── tests/                     # unit-тесты (особенно для core/)
├── build/                     # сборки (В .gitignore!)
└── .gitignore
```

> 🎯 **Ключевая папка — `core/`.** Там живёт чистая логика без движка. Её можно тестировать и (теоретически) перенести. Остальные слои — адаптеры вокруг неё.

## 11. Контроль версий (Git)

Git — ваша «машина времени» и страховка. Особенно важно при работе с ИИ: коммитьте маленькими шагами, чтобы откатить «галлюцинацию» ИИ одним движением.

### Базовый минимум команд
```bash
git init                       # создать репозиторий
git status                     # что изменилось
git add <файлы>                # добавить в индекс
git commit -m "сообщение"      # зафиксировать
git log --oneline              # история
git checkout <файл>            # откатить изменения файла
git revert <хэш>               # отменить конкретный коммит
```

### Что коммитить, а что нет (.gitignore)
- ✅ Коммитим: исходники кода, конфиги проекта, настройки движка, ассеты (если не гигантские).
- ❌ Игнорируем (через `.gitignore`): сборки (`build/`, `dist/`), временные/генерируемые движком папки (например, у Unity — `Library/`, `Temp/`, `Obj/`; у Godot — `.godot/`), файлы ОС (`.DS_Store`, `Thumbs.db`), файлы IDE (`.vscode/` по желанию, `*.csproj`/`*.sln` у Unity).
- 🐘 **Большие бинарники** (текстуры, модели, аудио) — через **Git LFS**, иначе репозиторий разбухнет.

### Культура коммитов
- **Маленькие, логичные коммиты** — одна мысль = один коммит.
- **Понятные сообщения** (правила Криса Бимса, сокращённо): заголовок в повелительном наклонении («Add enemy patrol state»), коротко — *что* и *почему* (не *как*).
- **Ветвление** (минимум): `main` — стабильная; feature-ветки для экспериментов (`feature/light-puzzle`).
- **Семантическое версионирование** для релизов (`v0.1.0`, `v0.2.0`) — на ранней стадии можно держать major=0.
- Помечайте коммиты с ИИ-кодом в описании — прозрачно для будущего себя.

## 12. Процесс разработки (MVP → итерации → полировка)

### Принцип «Сначала работает, потом чисто, потом быстро»
1. **Make it work** — прототип, который *играется*.
2. **Make it right** — рефакторинг в чистую модульную архитектуру.
3. **Make it fast** — оптимизация, и только где доказано узкое место.

### MVP и «найди фан как можно раньше»
- **MVP (Minimum Viable Product)** — минимально играбельная версия: движение → взаимодействие → очки/цель → конец.
- Сделайте MVP **быстро** и играйте сами. Цель — проверить, *интересно ли это вообще*, до того как вложите месяцы в ассеты/полировку.
- «Найди фан» (find the fun) на раннем этапе — иначе рискуете строить сложную систему вокруг неинтересной механики.

### Итерации и рефакторинг (мнение ветеранов)
- На старте код неизбежно будет «грязным» — это нормально, вы ещё не знаете, во что превратится игра.
- После прототипа — **архитектурируйте основные системы** (набросайте схему систем/данных как roadmap).
- Рабочий цикл профи: «быстро нагородил код, чтобы заработало → рефакторинг в чистую систему → мерж». Не оставляйте спагетти в `main` надолго.
- **Модульность через несколько рефакторингов:** делаете базовый минимум → добавляете фичу → рефакторите → следующая фича. Не пытайтесь сразу спроектировать «всё».

### Управление скоупом — ваш главный риск
- ПЕРВАЯ ИГРА почти всегда получается «грязной» — это нормально, это обучение.
- **Скоуп убивает больше первых игр, чем технические сложности.** Выберите игру, которую опишете одним предложением: «Платформер, где прыгаешь по облакам» лучше, чем «RPG с крафтом, мультиплеером и процедурной генерацией».
- Готовьтесь **закончить**: решите заранее, что значит «готово», иначе проект не закончится никогда.

### Журнал разработки (devlog)
- Ведите короткий devlog (даже в `docs/`). Это: документация, контекст для ИИ, мотивация и контент для портфолио/комьюнити.

## 13. Готовые шаблоны (AGENTS.md, structure, prompts)

### 13.1. Шаблон `AGENTS.md` (контекст для ИИ — положить в корень проекта)

> `AGENTS.md` — это **общий стандарт 2026 г.** (под эгидой Linux Foundation) для передачи контекста любому ИИ-инструменту. Claude Code читает `CLAUDE.md`, Gemini — `GEMINI.md`; чтобы не дублировать — держите `AGENTS.md` как единую правду, а в `CLAUDE.md`/`GEMINI.md` сделайте одну строку `@AGENTS.md` (импорт) или симлинк.
>
> **Держите файл коротким** (~до 150–200 строк) — слишком длинный снижает послушание ИИ. Узкоспециализированные правила выносите в вложенные `AGENTS.md` по подпапкам (`core/AGENTS.md`, `ui/AGENTS.md` и т.д.) — они подгружаются при работе с этими папками.

```markdown
# AGENTS.md — Threshold of Light

## Что это за проект
2D-игра [жанр]. Краткое описание: [1–2 предложения]. Платформы: [ПК/веб/мобильные].
Core loop: [действие → награда → прогресс]. Уникальная механика: [...].

## Технический стек
- Движок: [Godot 4.x / Unity / Phaser]
- Язык: [GDScript / C# / TypeScript]
- Менеджер пакетов/сборки: [...]

## Архитектура (ОБЯЗАТЕЛЬНО соблюдать)
- Слои: core (чистая логика, без движка) → game (use cases/controllers) → rendering/ui/audio/input/persistence.
- Правило зависимостей: зависимости только ВНУТРЬ, к core. Core НИЧЕГО не знает о движке/рендере/файлах.
- Состояния объектов — через FSM. Общение систем — через события (event bus).
- Синглтоны — редко; предпочитаем dependency injection / service locator.
- Логику держим в чистых функциях; побочные эффекты (рендер/звук/IO) — в адаптерах за интерфейсами (портами).

## Соглашения по коду
- Группируй файлы по фиче, не по типу.
- Один класс/модуль = одна ответственность (SRP).
- Короткие функции; выросло — разбивай.
```

### 13.2. Сильные промпт-шаблоны для работы с ИИ

> «Реализуй [функцию/состояние Y] в слое core/, без зависимостей от движка. Следуй соглашениям из AGENTS.md. Напиши unit-тесты».

**В) Отладка («почему падает»):**
> «Вот ошибка: [лог/трейс]. Вот код: [файл]. Ожидаемое поведение: [...]. Что уже пробовал: [...]. Найди причину».

**Г) Рефакторинг:**
> «Отрефактори [модуль] в чистую модульную структуру, не меняя поведение. Покрытие тестами уже есть — сначала убедись, что они зелёные».

**Д) В конце сессии — обновление контекста:**
> «Обнови docs/PROJECT_CONTEXT.md: что реализовано, текущее состояние, известные баги, ключевые решения и почему. Кратко, по делу».
