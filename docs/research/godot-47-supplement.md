## 1. Godot 4.7 — практический фундамент

### Игровой цикл вам ДАЮТ — не пишите его сами
В Godot не нужно реализовывать `while game_running: input/update/render`. Движок крутит цикл сам; вы лишь **вешаетесь** в нужные места:

- **`_process(delta)`** — вызывается каждый кадр, переменный шаг. Здесь — игровая логика, не зависящая от физики, ИИ, рендер-зависимые вещи.
- **`_physics_process(delta)`** — вызывается **с фиксированным шагом** (по умолчанию 60 раз/с). **Всё, что связано с физикой и `CharacterBody2D`/коллизиями, — только здесь.** Так движение стабильно и не «дрожит».
- **`_ready()`** — однажды, когда узел и его дети вошли в дерево. Инициализация.
- **`_enter_tree()` / `_exit_tree()`** — вход/выход из дерева (раньше `_ready`).

> 🎯 Правило для вас: **движение и столкновения — в `_physics_process`, остальное — в `_process`.** Не смешивайте — иначе «физика» начнёт зависеть от FPS.

### Узел (Node) — базовый кирпичик
Всё в Godot — узлы в дереве. Сцена (`.tscn`) — сохранённое поддерево = переиспользуемый «префаб». Композиция объектов = сборка из узлов (см. раздел 3).

### Дерево проекта (как у вас уже)
```
res://
  scenes/     → визуальные сцены (префабы): Main, Hub, CombatArena, Player…
  scripts/    → логика по доменам: core/, hub/, expedition/, combat/, progression/, persistence/
  data/       → *.tres ресурсы-определения (ModuleDefinition, EnemyDefinition…)
  tests/      → тесты
  assets/     → аудио, шрифты, текстуры
```
Это **правильная** структура: код — отдельно от сцен, данные (ресурсы) — отдельно, по доменам. Не ломайте её.

## 2. GDScript: статическая типизация и стиль

GDScript — динамически типизируемый, но **статическая типизация рекомендуется** (производительность + автодополнение + ловля ошибок на компиляции).

### Правила
- **Типизируйте всё, что можно:** переменные, аргументы, возвращаемые значения, сигналы.
- Вывод типа через `:=`: `var score := 0` (выведется `int`).
- **Типизированные массивы:** `var enemies: Array[Enemy] = []`.
- **Типизированные словари** (Godot 4.4+): `var stats: Dictionary[String, float] = {}`.
- **Безопасное приведение** через `as`: `var player: Player = get_node("Player") as Player`, затем `if player:` — не крашит, а даёт `null`.
- Включите в настройках редактора предупреждения/ошибки на нетипизированный код (Debugger →warnings), чтобы не расползалась «динамика».

```gdscript
class_name Player
extends CharacterBody2D

# Типизированные сигналы (Observer)
signal health_changed(new_health: int)
signal died

# @export — настраивается в инспекторе (ваш data-driven на уровне сцены)
@export var speed: float = 200.0
@export var max_health: int = 100
@export_group("Combat")
@export var attack_damage: int = 10

# @onready — инициализируется в _ready()
@onready var sprite: Sprite2D = $Sprite2D
@onready var animation: AnimationPlayer = $AnimationPlayer

# Приватные переменные — префикс _
var _health: int

func _ready() -> void:
    _health = max_health

func _physics_process(_delta: float) -> void:
    var direction := Input.get_vector("left", "right", "up", "down")
    velocity = direction * speed
    move_and_slide()

func take_damage(amount: int) -> void:
    _health = max(_health - amount, 0)
    health_changed.emit(_health)   # синтаксис Godot 4: .emit()
    if _health <= 0:
        died.emit()
```

### Когда статической типизации мало
GDScript с типами быстрее, но **не догоняет** C#/GDExtension (C++). Если когда-то появится узкое место (тысячи объектов, тяжёлый расчёт) — этот кусок переписывают на **C#** или **GDExtension (C++)**, остальное остаётся GDScript. Для вашего масштаба (5–12 мин забеги, граф из 7 узлов) **GDScript хватит с большим запасом**.

## 3. Узлы, сцены и компоненты (почему ECS вам НЕ нужен)

### Узлы и сцены = композиция
В Godot объект собирают **композицией узлов**, а не глубоким наследованием. Это и есть **Component-паттерн** (из «Game Programming Patterns»), только «компоненты» — это дочерние узлы/сцены.

> ⚠️ **Поправка к основному документу:** я там рекомендовал ECS как отдельный паттерн. **В Godot ECS не нужен и не нативен** (аддон godex — не мейнстрим, заброшен). Ваша **система узлов — это уже композиция**. Не городите ECS, пока не упрётесь в производительность на тысячах однотипных объектов (а это случается редко).

### Компоненты: один — одна ответственность
Храните переиспользуемые способности как отдельные компонент-сцены/узлы и собирайте из них сущности:

```
Player (CharacterBody2D)
├── HealthComponent     # может получать урон, имеет HP
├── HitboxComponent     # наносит урон
├── HurtboxComponent    # получает урон
├── MovementController
└── Sprite2D / AnimationPlayer
```

- **Crate** (ящик) = `[HurtboxComponent]` — может получить урон, но никому не навредит.
- **Trap** (ловушка) = `[HitboxComponent]` — наносит, но бессмертна.
- **Player/Enemy** = `[Health + Hitbox + Hurtbox + Movement]`.

Это и есть **композиция вместо наследования** и **SOLID/SRP**: меняете поведение — меняете набор компонентов, не трогая остальные.

> 💡 Это прямо ложится на вашу папку `scenes/entities/` — там живёт общая «библиотека» компонентов (`Hitbox`, `Hurtbox`, `Health`, …), которую переиспользуют и Player, и Enemy.

## 4. Ресурсы (.tres) — data-driven конфиги

**Resource** в Godot — это контейнер данных, сохраняемый как `.tres` (текст, дружелюбен к Git) или `.res` (бинарный). Это ваш **data-driven** механизм (аналог ScriptableObjects в Unity).

### У вас уже всё верно
Ваши `data/*` (`ModuleDefinition`, `EnemyDefinition`, `EncounterDefinition`, `ModifierDefinition`, `LootTable`) — это ровно оно. ✅

### Правила
- **Ресурс = данные/конфиг, а не состояние сессии.** Здоровье текущего игрока — НЕ в ресурсе; определение «у врага-гоблина 30 HP» — в ресурсе.
- **Ресурс — это ссылка и «переживает» смену сцен.** Если одна и та же сцена использует `game_states.tres`, её изменения видны всем. Осторожно: **не мутируйте общие ресурсы как рантайм-состояние** — для состояния забега держите отдельный объект.
- Делайте `@export` поля в скрипте ресурса, чтобы дизайн настраивался в инспекторе без кода.
- Наследование ресурсов (`resource_local_to_scene`, parent-наследование) — для вариаций (базовый «Тролль» → «Тролль-лучник»).

```gdscript
# data/enemies/enemy_definition.gd
class_name EnemyDefinition
extends Resource

@export var id: StringName
@export var display_name: String
@export var max_health: int = 20
@export var move_speed: float = 80.0
@export var attack_damage: int = 5
@export var loot_table: LootTable
```

## 5. Сигналы Godot vs ваш EventBus

В Godot есть **встроенные сигналы** — это нативная реализация Observer-паттерна. У вас есть ещё **свой `EventBus`**. Нужно чёткое правило, иначе два механизма начнут мешать друг другу.

### Правило «когда что»
| Ситуация | Инструмент |
|----------|-----------|
| Связь **внутри одной сцены** (кнопка → родитель) | **Сигналы узлов** (`signal x; x.emit()`) |
| Связь **между сценами / системами** (бой → HUD, экспедиция → хаб) | **EventBus (signal bus autoload)** |

### Event Bus (signal bus) — рекомендованный паттерн
Это тот самый «один autoload, который почти обязателен». Он почти не содержит кода/данных — только **список сигналов** для глобальных событий.

```gdscript
# scripts/core/event_bus.gd  (зарегистрировать как autoload "EventBus")
extends Node

signal run_started(seed: int)
signal run_ended(victory: bool)
signal enemy_killed(enemy_id: StringName)
signal resources_changed(amount: int)
signal module_built(module_id: StringName)
```
- **Излучатель:** `EventBus.enemy_killed.emit("goblin")`.
- **Слушатель:** где угодно `EventBus.enemy_killed.connect(_on_enemy_killed)` — без прямой ссылки друг на друга.

### Подводные камни
- Сигнал **уходит всем подписчикам** — при тысячах объектов это может бить по производительности (тогда для частых событий ищите другое решение).
- Удаление сигнала с шины = найти все излучатели, иначе **краш**. Редко, но болезненно.
- Передавайте ссылку на отправителя, чтобы получатель мог отфильтровать «это мне или нет».

## 6. Autoloads (синглтоны) — жёсткие правила

**Autoload** — это Godot-способ глобального доступа (проект → Project Settings → Autoload). У вас это, вероятно, `EventBus`, `GameState`, `SaveManager`, `SeedService`, `SimulationClock`.

### Ключевые правила (нарушения = хитрые баги)
1. **Никогда не обращайтесь к autoload в `_init()`** — его ещё нет. Только в `_ready()` / `_enter_tree()`.
2. **Никаких циклических зависимостей** между autoload'ами (`SaveManager` зависит от `GameState`, а `GameState` от `SaveManager` → дедлок/порядок инициализации). Развязывайте через сигналы или DI.
3. **Не храните состояние конкретной сцены** в autoload — он переживает смену сцен → утечки и «грязное» состояние. Сбрасывайте в `_ready()` или явным `reset()`.
4. **Лимит ~5–10 autoload'ов.** Больше → «God objects» и жёсткая связанность. Если их плодится — рефакторить, а не добавлять ещё.
5. **Порядок инициализации = сверху вниз** в списке Autoload. Не полагайтесь «само сложится». Порядок важен для зависимостей.
6. **Autoload — это НЕ «настоящий» синглтон** (его можно инстанцировать ещё раз). Это удобство глобального доступа, не гарантия единственности.

### Чек-лист «нужен ли autoload?» (все 4 — да)
- Данные действительно глобальны на всю игру?
- Должны переживать смену сцен?
- Нужны во многих местах?
- Их **нельзя** передать параметром/через сигнал?

Если хоть одно «нет» — используйте узел в дереве сцены, передавайте ссылку или излучайте сигнал.

> ⚠️ **ИИ по умолчанию лепит autoload рефлекторно** для любой shared-задачи. Это типичная ошибка. Заставляйте ИИ сначала спросить: «можно ли обойтись сигналом/параметром/service locator?» — и только потом/autoload.

## 7. Боевая система: hitbox/hurtbox + стейт-машины

### Hitbox / Hurtbox через Area2D
- **Hitbox** = `Area2D`, которая **наносит** урон (на оружие/атаке игрока).
- **Hurtbox** = `Area2D`, которая **получает** урон (на Player/Enemy).
- Кто кого бьёт — задаётся **collision layers/masks**, а не кодом.
- На пересечение: сигнал `area_entered(other: Area2D)` → передаём **объект данных атаки**.

```gdscript
# hitbox_component.gd
class_name HitboxComponent
extends Area2D

@export var attack_data: AttackData   # урон, элемент, тип, knockback…

func _ready() -> void:
    area_entered.connect(_on_area_entered)

func _on_area_entered(area: Area2D) -> void:
    var hurtbox := area as HurtboxComponent
    if hurtbox:
        hurtbox.take_hit(attack_data, owner)
```

- Выносите логику «разрешения удара» в функцию-посредника, например `CombatDirector.solve_attack(attack, aggressor, victim)` (у вас уже есть `CombatDirector` + `DamageSystem`!).
- **Не используйте `name` узла** как идентификатор — у sibling-инстансов имена автогенерируются.
- Активируйте hitbox в нужный момент анимации через **Call Method track** в `AnimationPlayer`.

### Стейт-машины (FSM) — для состояний
Базовый `State` + узел `StateMachine`, хранящий текущее состояние и переключающий по сигналу.

```gdscript
# state.gd
class_name State
extends Node
func enter() -> void: pass
func physics_update(_delta: float) -> void: pass
func exit() -> void: pass

# machine держит children-узлы-состояния и переключает current_state
```

### Важные нюансы (опыт Godot-сообщества)
- **FSM = одно активное состояние.** Но некоторые вещи сосуществуют (прыжок + атака). Решения: **несколько стейт-машин** (одна — движение, другая — действия) или **флаги**. Не запихивайте взаимоисключающее и сосуществующее в одну FSM.
- **Отделяйте логическое состояние от анимационного.** Анимация **выводится из** логического состояния (возможно с приоритетами), но **не обязана совпадать 1:1**.
- **FSM — инструмент, а не догма.** Когда перестаёт быть простым — прекращайте им пользоваться в этом месте.
- **«План, план, план»** — нарисуйте диаграмму состояний и переходов **до** кода. Это экономит рефакторинг.

> 🎯 Ваш `combat/` уже содержит `CombatDirector, DamageSystem, Hitbox/Hurtbox, FSM` — структура верная. Следите, чтобы FSM не разрастался до вложенных машин без нужды.

## 8. Жанр: структура забега (run loop)

Классический цикл roguelite/extractrun, **прямо ваш случай**:

```
[Хаб/Маяк] → [Старт экспедиции (seed)] → [Узел графа: бой/событие/лут]
   ↑                → [Выбор: идти дальше / эвакуироваться] ↺
   │                              ↓
   │                  [Эвакуация или смерть] → добыча/награда
   │                              ↓
   └──── [Постройка модулей в хабе] ← [Мета-прогресс/разблокировки]
```

За этот цикл отвечает отдельный **RunManager** — он **не** должен быть размазан по сценам.

## 9. RunManager: состояние забега vs мета-прогресс

**Самое важное архитектурное разделение в вашем жанре:**

```gdscript
# Концептуально (RunManager)
var current_run: RunState           # состояние ТЕКУЩЕГО забега — умрёт при конце
var meta: MetaProgressionData       # персистентно МЕЖДУ забегами (построено, разблокировано)

func start_new_run(seed: int) -> void: ...
func complete_node(result) -> void: ...
func end_run(victory: bool) -> void:
    # 1) добыча из current_run → переносим в meta
    # 2) current_run = null (чистим)
    # 3) сохраняем meta
```

| | `RunState` | `MetaProgressionData` |
|---|-----------|----------------------|
| Живёт | один забег (5–12 мин) | всю игру, между забегами |
| Примеры | текущая позиция в графе, собранный лут этого захода, HP разведчика в забеге | построенные модули маяка, разблокированные предметы, валюта-прогресс |
| Сохранять? | обычно нет (permadeath-дух); можно — для «продолжить забег» | **обязательно** |
| Чистить | при `end_run()` | никогда целиком |

> 🚨 **Типичный баг:** состояние забега «протекает» в мета (или наоборот) → после смерти/рестарта остаются «грязные» данные. Чёткий контрак: **что живёт в run, что в meta, что в save** — держите в `docs/ARCHITECTURE.md`.

Это прямо ложится на ваш `core/GameState` + `persistence/SaveManager` + `SaveSchema` + `SaveMigrations` — у вас уже заложен фундамент.

## 10. 🚨 Связка «модули ↔ экспедиции» — главный риск

Ваша мета-идея: **модули хаба меняют правила экспедиции, а экспедиции меняют хаб.** Это **двунаправленная** связь — классическое место, где рождается спагетти.

### Как проектировать (правило одного направления)
Не связывайте хаб и экспедию напрямую. Введите **явный посредник** и **однонаправленные пайплайны**:

```
 Хаб (построенные модули)
        │  (1) собираем «спецификацию забега» — однонаправленно вниз
        ▼
 [ModifierSystem / ExpeditionSpec]  ← посредник + данные-контракт
        │  (2) экспедиция читает spec, не знает про хаб
        ▼
 Экспедиция (забег по графу)
        │  (3) результат → dto «добыча/награда» — однонаправленно вверх
        ▼
 Хаб применяет добычу (через посредника, не напрямую в сущности хаба)
```

### Практически
- **Модуль → правило экспедиции:** модули описаны как данные (`ModifierDefinition`); `ModifierSystem` **собирает** их в плоский «контекст забега» (множитель урона, доступные враги, плотность лута…). Экспедиция принимает **готовый контекст**, ничего не зная о хабе.
- **Экспедиция → хаб:** забег возвращает **структуру результата** (`{resources, unlocks, stats}`), а не ссылки на свои внутренности. Хаб применяет результат через свой `BuildSystem`.
- **Ни хаб, ни экспедиция не ссылаются друг на друга напрямую.** Общение — через DTO + посредника (ваши `ModifierSystem`, `BuildSystem`).

> 💡 Это **Data-Driven + паттерн Посредник + DTO**. Так вы можете менять хаб, не трогая бой, и наоборот. Ваш `progression/ModifierSystem + UnlockSystem + BuildSystem` — правильное место для этого посредника.

## 11. Детерминизм и seeded RNG

У вас есть `SeedService` — это **критически важно** для roguelite: воспроизводимые забеги, отладка, «daily seed».

### Правила (опыт Godot-сообщества)
1. **Локальный** `RandomNumberGenerator` с сидом — **не** глобальный `randf()` для генерации.
   ```gdscript
   var rng := RandomNumberGenerator.new()
   rng.seed = run_seed
   var enemy_type := rng.randi_range(0, enemies.size() - 1)
   ```
2. **Сид задаётся один раз** в начале забега. **Никогда** не пересиживать (`seed = …`) на ходу — ломает последовательность.
3. **Порядок вызовов `rand` имеет значение.** Любой «лишний» случайный вызов (дробление урона, искры) рассинхронизирует генерацию уровня. Поэтому для генерации держите **отдельный** `rng`, к которому не лезет боёвка.
4. **Один общий генератор «на всё» — зло.** Заведите **отдельные потоки (streams)** под разные нужды: `gen_rng` (граф/уровень), `combat_rng` (бой), `loot_rng` (лут). Каждое ответвление можно породить от мастер-сида.
5. Для **кросс-устройственного** 100% детерминизма — **только целые числа**. Плавающая точка differs по архитектурам CPU и ломает воспроизводимость.

> 🎯 `SeedService` должен уметь выдать **под-сид** для каждой подсистемы (`graph_seed`, `loot_seed`, `combat_seed`), все детерминированно выведенные из мастер-сида. Тогда баг воспроизводится по сиду — бесценно для отладки.

## 12. Дизайн мета-прогресса (тренды 2026)

### Главное правило: ГОРИЗОНТАЛЬНЫЙ, не вертикальный
- ✅ **Открывайте разнообразие и новые механики:** новые предметы, модули, пути, альтернативные правила. Игрок на 100-м забеге имеет **больше опций**, а не «в 10 раз сильнее».
- ❌ **Ленивые проценты убивают мотивацию:** «+1% к скорости постройки» — игроку не за что зацепиться. 2026-тренд: «meta = новые механики/модификаторы, а не +X%».
- **Широта рано, глубина позже:** первые разблокировки резко расширяют пул опций; позже — нишевые/косметические.

### Балансировка
- Слишком сильная мета → **обесценивает скилл**.
- Слишком слабая → игрок «застревает», бросает.
- Нужна «золотая середина»: прогресс ощущается, но умение игрока — главный множитель.

### Controlled unpredictability (контролируемая случайность)
Современные roguelite уходят от «чистого рандома» к **управляемому**: взвешенные пулы лута, курируемые события, ветвящиеся апгрейды. Игрок **формирует вероятность**, а не только реагирует на удачу. → ваши `LootTable` (взвешенные) + выборы игрока.

### Модульность систем > «сырой» контент
Чтобы забеги не повторялись, делайте **модульные системы, которые умножают комбинации** (модификаторы × враги × модули × события), а не плодите контент вручную. Это ровно ваша модель «модули меняют правила».

## 13. Пулы предметов и модификаторов

Паттерн пула для рогалайта:

```gdscript
class_name ItemPool
extends Resource

# взвешенный список: [{id, weight, rarity}]
@export var entries: Array[WeightedItem]
var drawn_this_run: Array[StringName] = []   # без дублей в забеге

func draw(rng: RandomNumberGenerator, max_rarity: int = 99) -> StringName:
    var available := entries.filter(func(e): 
        return not e.id in drawn_this_run and e.rarity <= max_rarity)
    # ... взвешенный выбор по rng ...
    drawn_this_run.append(chosen)
    return chosen
```

- **Редкость и веса** — контроль «силы» и частоты.
- **Без дублей** в рамках забега (`drawn_this_run`).
- **Разблокировки входят в пул:** `meta`-прогресс добавляет id'ы в доступный пул, не трогая код боя.
- **Seed-детерминизм:** `draw(rng)` берёт ваш подконтрольный `rng`, не глобальный.

## 14. Тестирование в Godot (GUT / gdUnit4)

У вас есть `tests/`. В Godot два主流-фреймворка:

- **GUT (Godot Unit Test)** — самый популярный, GDScript-нативный.
- **gdUnit4** — альтернатива, ближе к xUnit-стилю.

### Что тестировать в первую очередь
- **`core/` (чистую логику)** — формулы урона, расчёт модификаторов, генерацию графа по сиду, правила эвакуации. Это самый ценный и легко тестируемый слой.
- **Детерминизм:** «тот же сид → тот же граф/лут» — идеальный unit-тест.

### Практики GUT
- **AAA:** Arrange → Act → Assert.
- **Одно утверждение на тест**, понятные имена `test_what_happens_when_condition`.
- `add_child_autofree()` — чтобы не было утечек памяти в тестах.
- Проверяйте **сигналы** (GUT умеет «слушать» сигналы).
- **Моки/заглушки** через `double()` и `stub()` — изолируйте зависимости.
- Интегрируйте тесты в **CI** (чтобы ловить регрессии).

> 💡 Поручайте ИИ генерацию тестов для `core/` как рутину — это его сильная сторона. Но читайте тесты.

## 15. Производительность в Godot (когда понадобится)

Не оптимизируйте заранее. Когда **профайлер** покажет узкое место:

- **Статическая типизация** везде (см. раздел 2) — дешёвый прирост.
- **`call_deferred` / framing** — тяжёлые операции разбивать по кадрам (например, генерация графа узлов).
- **Object Pool** — для снарядов/частиц/врагов (переиспользование вместо `queue_free()`/`new`).
- **`process_mode`** — ставить на паузу неактивные узлы вместо ручных проверок.
- **Избегать** частых `get_node()` в цикле — кешируйте в `@onready`.
- Если узкое место «честно» тяжёлое — переписать кусок на **C#** или **GDExtension (C++)**.

> Для вашего масштаба (5–12 мин забеги, 7 узлов, десятки врагов) производительность — **не ваша проблема на старте**. Сначала работающий вертикальный срез.

## 16. Производственный план: вертикальный срез для ВАШЕЙ игры

Жанровый микс (hub + extraction + roguelite + action) — **очень амбициозно для первого проекта**. Риск «построить всё сразу и утонуть» — главный. Поэтому:

### Фаза 0 — вертикальный срез (MVP)
Минимальный **замкнутый цикл**, чтобы проверить, что это **фан**:
1. **Хаб:** маяк + **1 слот модуля** + постройка 1 модуля.
2. **Экспедиция:** **1 узел** боя + **1 тип врага** + простой граф из 2–3 узлов + экстракция.
3. **Связь:** модуль меняет **одну** цифру в экспедиции (например, +урон); добыча из экспедиции → строит 1 модуль.
4. **Мета:** смерть/эвакуация возвращает в хаб, добыча сохраняется.
5. **Бой:** 1 атака игрока, 1 атака врага, hitbox/hurtbox, HP.

**Цель фазы 0:** пройти полный цикл «построй → иди → бей → эвакуйся → построй ещё» и почувствовать, **интересно ли это**.

### Фаза 1 — глубина механик
- Расширить граф до 7 узлов, добавить выбор «рисковать/уходить».
- Несколько модулей, несколько модификаторов (сайдгрейды, не проценты).
- Сиды/детерминизм + «daily seed».

### Фаза 2 — контент и полировка
- Больше врагов/энкаунтеров/лута через **пулы ресурсов** (без нового кода).
- UI/HUD, звук, juice (эффекты, тряска камеры).
- Баланс мета-прогресса.

### Несущий элемент — стройте первым
🚨 **Связку «модули↔экспедиции» (раздел 10) спроектируйте и обкатайте на фазе 0.** Это **несущая конструкция** — перекраивать её позже больнее всего.

### Гейм-дизайн чек-лист (положите в `docs/GAME_DESIGN.md`)
- [ ] Эскалатор в 1 предложении.
- [ ] Core loop нарисован.
- [ ] Список модулей/модификаторов с приоритетом (must / nice).
- [ ] Что в run-state, что в meta-state, что в save.
- [] Метрики «победы/поражения» забега.
- [] Мета-прогресс — **горизонтальный** (новые опции), не проценты.

2D hub-builder + extraction-lite + action-roguelite. Маяк на границе тёмного мира:

экспедиции, экспедиции меняют хаб.

- Godot 4.7.x stable, GDScript (GDScript 2.0). ПИНГИРУЙ версию — не советуй API других версий.

## Архитектура (ОБЯЗАТЕЛЬНО соблюдать)
- Слои: scripts/core/ (чистая логика, без узлов/движка) → домены hub/expedition/combat/progression → persistence.

- Связка «модули↔экспедиции» — ТОЛЬКО через посредника (ModifierSystem/BuildSystem) + DTO, без прямых ссылок.
- Сцены = композиция узлов (components). ECS НЕ ИСПОЛЬЗОВАТЬ.
- FSM — для состояний игрока/врагов/UI. Несколько машин при необходимости. Логическое состояние ≠ анимационное.

## Godot-правила (критично)
- Типизируй ВСЁ в GDScript (vars, args, returns, signals). Вывод через :=. Array[Type], Dictionary[K,V].
- Игровой цикл: движение/физика → _physics_process; остальное → _process. Не смешивать.
- Сигналы — внутри сцены; между сценами/системами — EventBus autoload.
- Autoloads: НИКОГДА не обращаться в _init() (только _ready). Без циклических зависимостей.
  Не хранить состояние конкретной сцены. Лимит 5–10. Не «настоящие» синглтоны.
- Прежде чем добавить autoload — спроси: можно ли обойтись сигналом/параметром/service locator?
- Ресурсы (.tres) — для данных/конфигов, НЕ для рантайм-состояния.
- RNG: локальный RandomNumberGenerator с сидом, отдельные потоки под subsystems, порядок вызовов важен. Глобальный randf() — только для некритичного.
- Hitbox/Hurtbox через Area2D + collision layers/masks. Разрешение удара — в CombatDirector/DamageSystem. Не использовать node name как id.

## Команды

- Тесты: [GUT / gdUnit4 — укажи команду запуска]
- Запрет: не запускать произвольные команды без нужды.

## Работа с ИИ
- Сначала план/архитектура, потом код. Дроби задачи. Читай доку Godot для незнакомого API.
