## 2. Что сделано хорошо

**Архитектура совпадает с экспертными паттернами из скиллов:**

- **ADR-005 (autoloads без `class_name`)** — соблюдён точно. Нет конфликта `Class "X" hides an autoload singleton`, и `EventBus`, `SeedService`, `GameState`, `SaveManager`, `SceneRouter` — все autoloads корректно зарегистрированы и доступны по имени.
- **ADR-003 (JSON int-кастинг)** — реализован идеально через `SaveSchema` с явным `int(d.get(...))` для каждого числового поля. Тест проверяет **типы**, не только значения (`typeof() == TYPE_INT`).
- **ADR-004 (мастер-сид ≤ 2^53−1)** — `SeedService` использует только целочисленные операции, деривация под-сидов через `_mix` (splitmix64-style) детерминирована и проверена на 500 мастер-сидах.
- **godot-combat-system** — реализован правильно: `DamageData` (RefCounted, enum AttackType), `HealthComponent` (i-frames, сигналы, без `target.health -= 10`), `Hurtbox` (только принимает, `monitorable=true`), `MeleeHitbox` (только в swing-окне, `set_deferred` для безопасного выключения). Урон ТОЛЬКО через `Hurtbox.take_attack` → `HealthComponent.take_damage`. HUD слушает `health_changed`/`died`, не мутирует.
- **godot-state-machine-advanced** — Pursuer использует типизированный enum, не строки; explicit `_change_state()` со сбросом `state_elapsed` и `attack_done`; нет вложенности > 3.
- **godot-save-load-systems** — `user://` для сохранений (не абсолютные пути), `version` поле, атомарная запись `.tmp → .bak → rename`, JSON парсится через `JSON.new()` (не `parse_string`), backup при ошибке чтения основного файла, файлы не зашифрованы (но и не нужны для оффлайн-игры). Всё по `save_integrity_validator.gd` (кроме SHA-256 — это опционально).
- **godot-gdscript-mastery** — типизированные сигналы, `Array[T]` где нужно, `@onready` для кеша, `_unhandled_input` для gameplay (не `_input`), signal-syntax (`signal.connect(callable)`, не string-based).
- **godot-characterbody-2d** — Scout/Pursuer используют `velocity` + `move_and_slide()`, движение в `_physics_process`, top-down (без coyote/buffer — не нужно).
- **process_mode = PROCESS_MODE_ALWAYS** — есть на CombatArena, HealthComponent, MeleeHitbox. Без этого hit-stop через `Engine.time_scale = 0.05` остановил бы обновления.

**Чистые тесты:**
- `combat_smoke.gd` — реальный сценарий, не моки: 5 проверок с абсолютными значениями (30→20, 100→75). Поймал баг HP в T-03 (см. LESSONS-T-03 урок 4).
- `run_tests.gd` — 75 проверок: порядок autoload'ов, отсутствие `class_name`, детерминизм сидов, JSON round-trip включая типы, atomic write, backup-failure, settings. Плюс `scene_flow_probe.gd` — изящный трюк: «бессмертный» пробочный узел у root переживает смену сцены, что позволяет тестировать переход сцен без self-freeze.

**SPEC-driven design** — спеки написаны *до* кода, и код им следует. Это редкость и большая ценность.

**Один разработчик сделал две большие сессии с одним коммитом на тикет** — чистая история в `прототип-дипсик` (T-02 + T-03).

## 3. Если бы начинал с нуля — что бы я сделал иначе

**Оговорка по итогам само-коррекции (§7):** ниже — только те архитектурные соображения, которые **актуальны для T-04 и Phase 1**. Преждевременные refactoring'и для T-03 (CombatTuning, CombatDirector, миграция на GUT, пересмотр `class_name`) — в §7, не здесь.

### 3.1. **Сразу `RouteGraph` как чистая RefCounted-функция, не Node**

Сейчас `RouteGraph` ещё не написан. Когда буду писать (T-04), он должен быть:
- `class_name RouteGraph extends RefCounted` (без сцены),
- метод `static func generate(master_seed: int) -> RouteGraphData`,
- **ноль импортов сцен** (проверяется грепом по `preload` и `Node` в файле),
- `RouteGraphData` — отдельный `RefCounted` с `nodes: Array`, `edges: Array`, методы `is_connected()`, `extraction_depth_min()`, и т.д.

Это даёт:
- Тестируемость без движковой сцены (GUT в Phase 2, или наш `run_tests.gd`).
- Детерминизм в чистом виде — функция от seed, без сайд-эффектов.
- Сцена `expedition_map.tscn` — чисто view, получает `RouteGraphData` и рисует.

### 3.2. **Сразу ввести `NodeType` enum/constants**

`SceneRouter._on_node_entered` сравнивает `node_type == 0` как COMBAT — магическое число, явно признанное в комментарии как «появится в T-04». Сейчас — самое время:

```gdscript
# scripts/expedition/node_type.gd
class_name NodeType
const COMBAT := 0
const EVENT := 1
const RESOURCE := 2
const CAMP := 3
const EXTRACTION := 4
const ELITE := 5
const START := 100
const GUARDIAN := 101
```

`int` константы совместимы с `signal node_entered(node_type: int)`, и не требуют менять сигнатуру. Когда T-04 добавит настоящие типы узлов, `SceneRouter` сразу пишет `if node_type == NodeType.COMBAT:`.

### 3.3. **Не вводить `combat_requested` в EventBus** (или пометить DEBUG)

`EventBus.combat_requested()` — это T-03-приспособление для тестового входа в арену из хаба. По правилу godot-signal-architecture: «Global Bus: ONLY for lifecycle events (< 15)». `combat_requested` — НЕ lifecycle, а debug-маршрут. Когда T-04 закроет нормальный вход через карту, этот сигнал умрёт.

Если бы начинал сначала — не добавлял бы его в EventBus, а в HubScreen `_unhandled_key_input` ловил бы F-клавишу и вызывал `SceneRouter._goto(COMBAT_ARENA_SCENE)` напрямую. Сейчас — **минимум**, что нужно: переименовать в `EventBus.debug_combat_requested()` с комментарием, чтобы не забыть удалить в T-04.

### 3.4. **Documentation drift держать в актуальности** (рабочий процесс)

Это не «как бы я переделал код», а про рабочий процесс. В проекте сейчас есть расхождения, которые я заметил:

- `README.md` п.8: FSM 4 состояния. SPEC-04 §5: 5. В коде T-03 — 5. README **не обновлён** (T-03 §«Действие: README п.8 привести к 5 состояниям» было запланировано, но не сделано).
- `CONTEXT.md` говорит «7 узлов». `SPEC-03 §1` уже выбрал «7 рядов». README/CONTEXT **не обновлены** (ждёт ADR-006).
- ADR-002: «Accepted». `OPEN-QUESTIONS.md` Q-05: «гипотеза-прототипа». Это формально не противоречие, но семантически — разные уровни уверенности.

Если бы начинал сначала, я бы сразу ввёл правило: «изменил ADR → grep по `OPEN-QUESTIONS.md` и обнови статусы → grep по `README.md` и `CONTEXT.md` и обнови формулировки». Сейчас это ручная работа, и она провисает.

## 7. Само-коррекция: где я перегнул в первоначальном обзоре

**Этот раздел — ключевой.** В первой версии обзора я предложил четыре вещи, которые не подходят для текущей фазы проекта. Спасибо владельцу за обратную связь — без неё эти претензии ушли бы в `REVIEW-2026-08-03.md` и соблазнили бы кого-то начать преждевременный refactoring.

### 7.1. ~~Догматизм в отношении `class_name`~~ — **ОТКЛОНЕНО**

**Что я предлагал:** убрать `class_name` у скриптов, привязанных к сценам (Scout, Pursuer, CombatArena), аргументируя это «смешиванием презентации и данных». Предлагал вынести всё в `.tres` ради «чистоты».

**Почему это было неправильно:**
- В Godot 4.x объявление `class_name` на GDScript-нодах — это **стандартный способ** получить статическую типизацию (`var scout: Scout`) и проверки `is Scout`.
- В тестах T-03 (`combat_smoke.gd`) уже используется `var enemy: Node` — переход на `var enemy: Pursuer` с `class_name` сделает код чище.
- Выносить всё в `.tres` ради «чистоты» на этапе прототипа — бессмысленное усложнение. `.tres` полезны для **данных** (ModuleDefinition, EnemyDefinition), не для **логики** (Scout FSM, Pursuer FSM).
- Текущая организация «`class_name Scout` в `scenes/combat/scout.gd`» — идиоматична для Godot 4.

**Вердикт:** не трогать до Phase 2. Если в Phase 2 появится несколько разных scout'ов (например, разные классы), можно подумать о наследовании, но это не текущая задача.

### 7.2. ~~Преждевременное расщепление `CombatArena`~~ — **ОТКЛОНЕНО до Phase 2**

**Что я предлагал:** выделить `CombatTuning` Resource (заменить `arena.get_parameter("dash_cooldown", 0.8)` на `arena.tuning.dash_cooldown`) и `CombatDirector` (отдельно от `CombatArena`).

**Почему это было преждевременным:**
- Для T-03 монолитная `CombatArena` была адекватным изолированным стендом: один scene, один скрипт, все параметры в `DEFAULTS`/`RANGES` dictionaries. Это читается одним экраном, это тестируется в `combat_smoke.gd` напрямую.
- Дробление на 3 сущности (Tuning + Director + Arena) звучит красиво с точки зрения SOLID, но для боевой арены с 6 ползунками и 2 преследователями — это **over-engineering**.
- Параметры в `Dictionary` (с дефолтами и RANGES) — это валидный паттерн для централизованного тюнинга в greybox-фазе. Inspector-редактируемость через Resource — это правильно для production, но greybox-фаза заканчивается с T-07.
- `notify_*_died` от Scout/Pursuer — это «call down», и **это правда нарушение** принципа «Signal Up, Call Down». Но это **мелкое** нарушение: `HealthComponent.died` уже эмитится, и `CombatArena.notify_*_died` лишь форвардит наружу. Перевести на чистые сигналы — **стоит сделать**, но это не требует расщепления `CombatArena`. Достаточно убрать `notify_*_died` и подписаться на `health.died` в `_ready` CombatArena.

**Вердикт:** **не делать** расщепление на CombatTuning/CombatDirector. Делать только переход `notify_*_died` → сигналы (п. 8 из §5), и только если это естественно ложится в начало T-04.

### 7.3. ~~Навязывание GUT~~ — **ОТКЛЕНО (YAGNI)**

**Что я предлагал:** перейти с кастомного `run_tests.gd` на GUT (Godot Unit Test).

**Почему это было неправильно:**
- `run_tests.gd` за миллисекунды выполняет 75 проверок в headless-режиме на CI и Windows.
- Кастомный раннер закрывает текущие задачи на 100%: типизированные `_check(condition, label)`, `print` в stdout, `quit(0/1)` по результату.
- GUT добавит: новую зависимость (`addons/gut/plugin.cfg`), новый CLI-протокол, новый conventions. Это стоимость без выгоды на текущем объёме.
- Миграция осмыслена, когда тестов > 200 и появляются GUT-специфичные потребности (signal spies, parameterized tests, before_each).

**Вердикт:** не мигрировать. Если T-04..T-07 принесут > 200 проверок и тесты на сигналы (через `watch_signals`) — вернуться к обсуждению.

### 7.4. ~~Драматизация UID-варнинга~~ — **ПОНИЖЕН ПРИОРИТЕТ**

**Что я предлагал:** назвать 14-символьный UID в `main_menu.tscn` «главным не-архитектурным моментом».

**Почему это было преувеличением:**
- `tools/build.cmd` и `tools/test.cmd` проходят с кодом 0. Сборка работает.
- Это мелкий варнинг импорта, не критическая проблема.
- Возможно, при импорте Godot 4.7.1 молча обрезает UID до 13 символов; round-trip в редакторе всё равно сработает.

**Вердикт:** оставить в §5 как пункт 1 (мини-улучшение), но не выносить в TL;DR и не помечать как блокер. Если владелец правит в редакторе — отлично; если нет — не страшно.

### 7.5. ~~SHA-256 integrity check~~ — **ОСТАВЛЕНО как опциональное**

`save_integrity_validator.gd` из скилла рекомендует SHA-256 для отлова «повреждённый JSON, но синтаксически валидный». Это не перегиб — это реальный класс багов. Но не блокер, потому что:
- Атомарная запись `.tmp → .bak → rename` уже покрывает 95% случаев (процесс убит между шагами → `.bak` остался).
- Случай «файл валидный, но данные испорчены» (бит-флип) — крайне редок на SSD.

**Вердикт:** оставить в §5 как опциональное улучшение. Делать, если T-06 (телеметрия/симулятор) покажет реальные проблемы с целостностью.

## 8. Что я выучил из этой само-коррекции

1. **Не предлагать refactoring'и, которые не вызваны текущей болью.** «Это было бы SOLID-нее» — не причина, если код читается и тестируется.
2. **Сверять свой обзор с реальным масштабом проблемы.** «Монолитная `CombatArena` на 90 строк с 6 ползунками» — это не монолит, это плотный код. SOLID-разбиение для 90 строк — это просто больше файлов без выгоды.
3. **Учитывать convention инструмента.** В Godot 4.x `class_name` на нодах — это convention, а не антипаттерн. Экспертные скиллы (`godot-composition`, `godot-state-machine-advanced`) **используют** `class_name` повсеместно.
4. **YAGNI применять и к обзорам тоже.** Рекомендация «может пригодиться в Phase 2» — это не повод писать её в Phase 1.
5. **Варнинги ≠ ошибки.** UID-варнинг и тест на `process_frame.connect` в `scene_flow_probe` — оба живут в проекте и оба не блокируют. Не путать уровни серьёзности.
