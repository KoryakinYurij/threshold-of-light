## 2. Что сделано хорошо

**Архитектура совпадает с экспертными паттернами из скиллов:**

- **ADR-005 (autoloads без `class_name`)** — соблюдён точно. Нет конфликта `Class "X" hides an autoload singleton`, и `EventBus`, `SeedService`, `GameState`, `SaveManager`, `SceneRouter` — все autoloads корректно зарегистрированы и доступны по имени. **Заметьте: `class_name` запрещён ADR-005 ТОЛЬКО для autoload-синглтонов. Для всех остальных скриптов (Scout, Pursuer, CombatArena, HubScreen, ModuleDefinition, EncounterDefinition, …) `class_name` в PascalCase прямо предписан — это convention, а не нарушение.** Подробнее см. §3.3.
- **ADR-003 (JSON int-кастинг)** — реализован идеально через `SaveSchema` с явным `int(d.get(...))` для каждого числового поля. Тест проверяет **типы**, не только значения (`typeof() == TYPE_INT`).
- **ADR-004 (мастер-сид ≤ 2^53−1)** — `SeedService` использует только целочисленные операции, деривация под-сидов через `_mix` (splitmix64-style) детерминирована и проверена на 500 мастер-сидах.
- **godot-combat-system** — реализован правильно: `DamageData` (RefCounted, enum AttackType), `HealthComponent` (i-frames, сигналы, без `target.health -= 10`), `Hurtbox` (только принимает, `monitorable=true`), `MeleeHitbox` (только в swing-окне, `set_deferred` для безопасного выключения). Урон ТОЛЬКО через `Hurtbox.take_attack` → `HealthComponent.take_damage`. HUD слушает `health_changed`/`died`, не мутирует.
- **godot-state-machine-advanced** — Pursuer использует типизированный enum, не строки; explicit `_change_state()` со сбросом `state_elapsed` и `attack_done`; нет вложенности > 3.
- **godot-save-load-systems** — `user://` для сохранений (не абсолютные пути), `version` поле, атомарная запись `.tmp → .bak → rename`, JSON парсится через `JSON.new()` (не `parse_string`), backup при ошибке чтения основного файла, файлы не зашифрованы (но и не нужны для оффлайн-игры). Всё по `save_integrity_validator.gd` (кроме SHA-256 — это опционально).
- **godot-gdscript-mastery** — типизированные сигналы, `Array[T]` где нужно, `@onready` для кеша, `_unhandled_input` для gameplay (не `_input`), signal-syntax (`signal.connect(callable)`, не string-based).
- **godot-characterbody-2d** — Scout/Pursuer используют `velocity` + `move_and_slide()`, движение в `_physics_process`, top-down (без coyote/buffer — не нужно).
- **process_mode = PROCESS_MODE_ALWAYS** — есть на CombatArena, HealthComponent, MeleeHitbox. Без этого hit-stop через `Engine.time_scale = 0.05` остановил бы обновления.

**Чистые тесты:**
- `combat_smoke.gd` — реальный сценарий, не моки: 5 проверок с абсолютными значениями (30→20, 100→75). Поймал баг HP в T-03 (см. LESSONS-T-03 урок 4).
- `run_tests.gd` — 75 проверок: порядок autoload'ов, отсутствие `class_name` у autoload'ов, детерминизм сидов, JSON round-trip включая типы, atomic write, backup-failure, settings. Плюс `scene_flow_probe.gd` — изящный трюк: «бессмертный» пробочный узел у root переживает смену сцены, что позволяет тестировать переход сцен без self-freeze.

**SPEC-driven design** — спеки написаны *до* кода, и код им следует. Это редкость и большая ценность.

**Один разработчик сделал две большие сессии с одним коммитом на тикет** — чистая история в `прототип-дипсик` (T-02 + T-03).

## 3. Если бы начинал с нуля — что бы я сделал иначе

### 3.1. **`CombatTuning` Resource сразу, а не `arena.get_parameter()`**

Сейчас Scout/Pursuer читают параметры через арену как service locator:
```gdscript
arena.get_parameter("dash_cooldown", 0.8)
```

Это coupling (Scout знает про Arena) и теряет типобезопасность (строки + `float`).

`godot-resource-data-patterns` (Workflow 3 «Data-Driven Systems») прямо требует:
> Create ONE `ItemData.gd` extending `Resource`. Instantiate it as 100 `.tres` files instead of 100 scripts.
> The HUD NEVER references the Player directly. It listens for `player_health_changed` on the Signal Bus.
> Enable "Local to Scene" on ALL `@export Resource` variables, or call `resource.duplicate()` in `_ready()`. Failure to do this is Bug #1 in Part 8.

А `godot-combat-system` §Available Scripts требует `damage_data.gd` как typed `DamageData` **Resource** с `enum`/flags для damage types. Контракт «параметры через Resource» — это не косметика, а требование скилла.

Лучше было бы сразу:
```gdscript
# scripts/combat/combat_tuning.gd
class_name CombatTuning extends Resource
@export var iframes: float = 0.18
@export var dash_cooldown: float = 0.8
@export var telegraph: float = 0.5
@export var enemy_damage: int = 25
@export var scout_hp: int = 100
@export var speed: float = 220.0
signal changed
```

CombatArena держит `tuning: CombatTuning` как свойство. TuningPanel пишет в `arena.tuning.iframes = 0.25` (или `arena.tuning.set_value("iframes", 0.25)` с emit `changed`). Scout/Pursuer слушают `arena.tuning.changed` или читают напрямую `arena.tuning.dash_cooldown` — типизированно, без magic strings, Inspector-редактируемо.

Бонус: можно сохранять разные `tuning.tres` для разных сценариев (сложный враг → `tuning_hard.tres`).

**В Phase 1 T-04 это можно внедрить без потерь** — текущая арена ещё не разрослась, и переписать `parameters: Dictionary` на `tuning: CombatTuning` — это 30-минутный таск.

### 3.2. **Перевести `notify_*_died` со «call down» на «signal up»**

`scout.gd` и `pursuer.gd` **вызывают вниз**:
```gdscript
arena.notify_scout_died()
arena.notify_enemy_died(self)
```

Это прямое нарушение `godot-signal-architecture`:
> Signal Up / Call Down: Children → parents: past-tense signals (`health_changed`, `died`). Parents → children: direct calls / properties.
> NEVER mutate external state from a component.

`HealthComponent.died` уже эмитится. Достаточно:
- Убрать `arena.notify_*_died()` из Scout/Pursuer.
- В `CombatArena._ready()` подписаться на `scout.health.died` и `pursuer.health.died`.
- `died`-обработчик делает то, что раньше делал `notify_*_died`.

Это 15-минутный таск, который сразу установит правило для остального проекта. Делать в начале T-04, до написания ExpeditionController.

**Попутно — `CombatDirector` отдельным node**: `godot-composition` и `godot-state-machine-advanced` рекомендуют, чтобы FSM-логика жила в `StateComponent` под composition-корнем, а не в монолитной `CombatArena`. Для T-03 монолит был адекватен, но для T-04, когда `CombatArena` начнёт спавнить врагов динамически по `depth` (K(d) формула, SPEC-04 §4), логика разрастётся. Имеет смысл выделить `CombatDirector` (Node) — он владеет `current_run`, спавнит врагов, считает награды, эмитит `EventBus.node_cleared`. `CombatArena` остаётся чисто визуальной (фон, стены, камера). Это **на T-04, не на T-03** — раньше не было материала для расщепления.

### 3.3. **Никогда не убирать `class_name` у сцена-привязанных скриптов** (это предписано)

**Моя первоначальная претензия в обзоре «3.3» была ошибочной.** Проверил против ADR-005, CONTEXT.md и скиллов:

**ADR-005 §Decision:**
> **Автолоад-синглтоны не объявляют `class_name`.** Имя автолоада — единственная точка входа.
> Обычные (не-автолоад) классы правило 1 сохраняют без изменений: `RunState`, `HubState`, `ProfileState`, `HubScreen`, `EnemyDefinition` объявляют `class_name` в PascalCase, потому что автолоадами они не являются.

**CONTEXT.md, раздел «Naming»:**
> Scene and script files: snake_case (e.g., `hub_screen.tscn`, `hub_screen.gd`) — Godot convention; `class_name` and node names stay PascalCase (e.g., `HubScreen`)

**Скиллы** (godot-gdscript-mastery §Quick Landmines, godot-composition, godot-state-machine-advanced, godot-combat-system) повсеместно используют `class_name` на сцена-привязанных GDScript-классах: `class_name Scout extends CharacterBody2D`, `class_name Pursuer extends CharacterBody2D`, и т.д. Это **convention Godot 4.x** для статической типизации (`var scout: Scout`) и проверок `is Scout`.

**Вердикт:** `class_name Scout` в `scenes/combat/scout.gd` — это идиоматично и предписано. Не трогать. Это моя единственная фактическая ошибка в первоначальном обзоре (признана в §7).

### 3.4. **Сразу `RouteGraph` как чистая RefCounted-функция, не Node**

Когда буду писать `RouteGraph` (T-04), он должен быть:
- `class_name RouteGraph extends RefCounted` (без сцены),
- метод `static func generate(master_seed: int) -> RouteGraphData`,
- **ноль импортов сцен** (проверяется грепом по `preload` и `Node` в файле — это явный DoD из SPEC-03 §8),
- `RouteGraphData` — отдельный `RefCounted` с `nodes: Array`, `edges: Array`, методы `is_connected()`, `extraction_depth_min()`, и т.д.

Это даёт:
- Тестируемость **через GUT 9.7.1** (см. §3.5) — без движковой сцены.
- Детерминизм в чистом виде — функция от seed, без сайд-эффектов.
- Сцена `expedition_map.tscn` — чисто view, получает `RouteGraphData` и рисует.

### 3.5. **Подключить GUT 9.7.1 сразу, не откладывать**

**Моя первоначальная претензия «GUT — YAGNI» была ошибочной.** Проверил:

- **SPEC-03 §5: «Тесты генератора, `tests/unit/test_route_graph.gd`, GUT 9.7.1 (`godot_4_7`)»** — спека T-04 прямо требует GUT 9.7.1 для тестов `RouteGraph`.
- **phase-1-readiness-audit.md §2 п.9: «GUT без пина версии. godot-47-supplement §14, production-supplement §4.1. Для Godot 4.7.x — GUT 9.7.1 (ветка `godot_4_7`; таблица версий [bitwes/Gut]). Пин внесён в оба документа»** — это критично для T-04.
- **CI-гейт 1000 сидов на инвариант** из SPEC-03 §5 — кастомный `run_tests.gd` не имеет GUT-овского `assert_eq`/`assert_true`, а кастомный `_check(condition, label)` менее выразителен. GUT нужен **именно для T-04**, не для T-02/T-03.
- Полный прогон 10 000 сидов перед этапными релизами (SPEC-03 §5) — GUT поддерживает parameterised tests, кастомный раннер — нет.

Кастомный `run_tests.gd` закрывает задачи T-02/T-03. Но T-04 требует GUT, и **откладывать подключение GUT нельзя** — это будет означать переписывать T-04-тесты дважды.

**Вердикт:** в начале T-04 подключить `addons/gut/plugin.cfg` (GUT 9.7.1, ветка `godot_4_7`), `git add` его в репо, и писать `test_route_graph.gd` уже на GUT.

### 3.6. **Сразу ввести `NodeType` enum/constants**

`SceneRouter._on_node_entered` сравнивает `node_type == 0` как COMBAT — магическое число, явно признанное в комментарии как «появится в T-04». Сейчас — самое время:

```gdscript
# scripts/expedition/node_type.gd
class_name NodeType
const COMBAT := 0
const EVENT := 1
const RESOURCE := 2
const CAMP := 3
const EXTRACTION := 4
const ELITE := 5
const START := 100
const GUARDIAN := 101
```

`int` константы совместимы с `signal node_entered(node_type: int)`, и не требуют менять сигнатуру. Когда T-04 добавит настоящие типы узлов, `SceneRouter` сразу пишет `if node_type == NodeType.COMBAT:`.

### 3.7. **Не вводить `combat_requested` в EventBus** (или пометить DEBUG)

`EventBus.combat_requested()` — это T-03-приспособление для тестового входа в арену из хаба. По правилу `godot-signal-architecture`:
> Global Bus (Autoload): ONLY for lifecycle events (`match_started`, `player_died`, `settings_changed`). Debugging sprawl is the cost — limit events to < 15.

`combat_requested` — НЕ lifecycle, а debug-маршрут. Когда T-04 закроет нормальный вход через карту, этот сигнал умрёт.

Если бы начинал сначала — не добавлял бы его в EventBus, а в HubScreen `_unhandled_key_input` ловил бы F-клавишу и вызывал `SceneRouter._goto(COMBAT_ARENA_SCENE)` напрямую. Сейчас — **минимум**, что нужно: переименовать в `EventBus.debug_combat_requested()` с комментарием, чтобы не забыть удалить в T-04.

### 3.8. **Не откладывать исправление UID в `main_menu.tscn`**

**Моя первоначальная оценка «мелкий варнинг, не блокер» была ошибочной.** Проверил README §Development:

> Все файлы (`project.godot`, `.tscn`) написаны текстом вручную. Признаки: нет `.godot/`, нет `*.import`-сайдкаров у ассетов, нет `*.uid`-сайдкаров у скриптов, а `main_menu.tscn` ссылается на скрипт через `path=` без `uid=`.
>
> Отсюда следствие, которое важно знать до первого коммита сцен: **UID в `main_menu.tscn` недействителен**. Там стоит `uid="uid://bq6v0xmainmenu"` — 14 символов после `uid://`, тогда как движок (`core/io/resource_uid.cpp`) допускает максимум 13

README явно прописывает это как **Known Issue с инструкцией по исправлению**:

> **Правильный порядок действий, а не ручная правка UID:**
> 1. Открыть проект в Godot 4.7.x — редактор создаст `.godot/`, сгенерирует `*.import` и `*.uid`.
> 2. Пересохранить `main_menu.tscn` (Ctrl+S) — движок перепишет UID на валидный и добавит `uid=` в ссылку на скрипт.
> 3. **Закоммитить** появившиеся `*.uid` и `*.import` — они часть состояния проекта, не артефакты сборки.

T-02 отчёт говорит, что проект открывался в редакторе, но `.uid` мог не закоммититься, или `main_menu.tscn` не пересохранялся. Это **не драматизация — это конкретный пункт из Known Issues README**, который требует ручного действия.

### 3.9. **Documentation drift держать в актуальности** (рабочий процесс)

## 4. Что подправить в следующих шагах (T-04..T-07)

### T-04 — Экспедиция (следующий)

## 7. Само-коррекция после верификации

**Этот раздел — ключевой.** В первой версии этого документа (T-04-review-before-correction) я в разделе «Само-коррекция» отверг четыре замечания обзора. После повторной проверки против ADR-005, SPEC-03, README.md, phase-1-readiness-audit.md и скиллов `.agents/skills/` выяснилось: **три из четырёх отвергнутых замечаний были верными**. Ниже — по каждому пункту.

### 7.1. ~~Догматизм в отношении `class_name`~~ — **МОЯ ЕДИНСТВЕННАЯ ФАКТИЧЕСКАЯ ОШИБКА**

**Что я предлагал в обзоре «3.3»:** убрать `class_name` у скриптов, привязанных к сценам (Scout, Pursuer, CombatArena), аргументируя это «смешиванием презентации и данных». Предлагал вынести всё в `.tres` ради «чистоты».

**Что говорит проект:**
- **ADR-005 §Decision (дословно):** «**Обычные (не-автолоад) классы правило 1 сохраняют без изменений:** `RunState`, `HubState`, `ProfileState`, `HubScreen`, `EnemyDefinition` объявляют `class_name` в PascalCase, потому что автолоадами они не являются».
- **CONTEXT.md, раздел «Naming»:** «`class_name` and node names stay PascalCase (e.g., `HubScreen`)».
- Скиллы `godot-gdscript-mastery`, `godot-composition`, `godot-state-machine-advanced`, `godot-combat-system` повсеместно используют `class_name` на сцена-привязанных GDScript-классах.

**Вердикт:** `class_name Scout` в `scenes/combat/scout.gd` — это идиоматично и **прямо предписано** ADR-005/CONTEXT. Моя претензия ошибочна. См. §3.3 — там исправленный текст.

### 7.2. ~~Преждевременное расщепление `CombatArena`~~ — **ОТКЛОНЕНО мной ОШИБОЧНО**

**Что я отверг в обзоре «3.1, 3.2»:** предложения вынести `CombatTuning` Resource и `CombatDirector` отдельным node.

**Что говорят скиллы:**
- `godot-resource-data-patterns` §Workflow 3: «Create ONE `ItemData.gd` extending `Resource`. Instantiate it as 100 `.tres` files instead of 100 scripts. The HUD NEVER references the Player directly. It listens for `player_health_changed` on the Signal Bus.»
- `godot-resource-data-patterns` §NEVER Do: «NEVER use untyped arrays in Resources. `@export var items: Array` allows logic errors. Always use `Array[ResourceClass]` for type safety» — это прямое указание на то, что `parameters: Dictionary` (без типа) в CombatArena нарушает паттерн.
- `godot-signal-architecture` §NEVER Do: «NEVER mutate external state from a component. If `HealthComponent` calls `$HUD.update_bar()`, deleting the HUD crashes the game. Components emit signals; listeners decide how to respond» — и `arena.notify_*_died()` от Scout/Pursuer — это ровно «mutate external state from a component» в обратную сторону: компонент дёргает parent.
- `godot-combat-system` §NEVER Do: «NEVER couple UI lifebars inside the Player script — Emit `health_changed`; HUD listens» — и в `arena.notify_*_died` Scout знает про `arena`-получателя, что и есть coupling.

**Вердикт:** `CombatTuning` Resource и переход на сигналы `HealthComponent.died` — это **прямые требования скиллов**, а не «premature refactoring». Расщепление `CombatArena` на `CombatDirector`+`CombatArena` — фаза 2, но `CombatTuning` и сигналы можно делать в начале T-04 (см. §3.1, §3.2, §5.8, §5.10).

### 7.3. ~~Навязывание GUT~~ — **ОТКЛОНЕНО мной ОШИБОЧНО (YAGNI — неправильный аргумент)**

**Что я отверг в обзоре «3.5»:** предложение подключить GUT для T-04.

**Что говорят спеки и audit:**
- **SPEC-03 §5:** «`tests/unit/test_route_graph.gd`, GUT 9.7.1 (`godot_4_7`)** — спека **прямо требует GUT** для тестов `RouteGraph`.
- **phase-1-readiness-audit.md §2 п.9:** «GUT 9.7.1 — пин внесён в оба документа» (godot-47-supplement §14, production-supplement §4.1). Audit явно требует пина.
- **CI-гейт 1000 сидов на инвариант + полный прогон 10 000** — GUT поддерживает parameterised tests, кастомный `run_tests.gd` — нет.

**Вердикт:** GUT 9.7.1 обязателен для T-04, и подключать его надо в начале T-04 (или сейчас, мини-улучшение №2). YAGNI здесь не применим — это прямое требование спецификации. См. §3.5, §5.2.

### 7.4. ~~Драматизация UID-варнинга~~ — **ОТКЛОНЕНО мной ОШИБОЧНО**

**Что я отверг в обзоре «3.8»:** предложение считать 14-символьный UID блокером.

**Что говорит README §Development (дословно):**
> Строка переполняет uint64 при парсинге, и редактор молча заменит её при первом сохранении сцены (прогон алгоритма `text_to_id` даёт `uid://xlpavb8by0sw` — round-trip не сохраняется).
> **Правильный порядок действий, а не ручная правка UID:** 1) Открыть проект в Godot 4.7.x… 2) Пересохранить `main_menu.tscn` (Ctrl+S)… 3) **Закоммитить** появившиеся `*.uid` и `*.import` — они часть состояния проекта, не артефакты сборки

README явно прописывает это как **Known Issue с инструкцией по исправлению**, а не как «мелкий варнинг импорта». T-02 отчёт говорит, что проект открывался в редакторе — но `main_menu.tscn` либо не пересохранялся, либо `.uid`-файлы не были закоммичены. Это нужно проверить и доделать.

**Вердикт:** UID — это не драматизация, а **конкретный пункт из Known Issues README** с явной инструкцией. Делать в начале T-04 (или сейчас, мини-улучшение №1). См. §3.8, §5.1.

## 8. Что я выучил из этой коррекции

1. **Перед тем как отвергать замечание, сверяться с ADR/SPEC/README и скиллами**, а не только с «ощущением» масштаба проблемы. Я отверг GUT, UID и CombatTuning на основании «YAGNI/over-engineering/мелкий варнинг» — все три оценки противоречили прямым требованиям проекта.

2. **Конвенция инструмента важнее «чистоты» в чьей-то голове.** ADR-005 прямо говорит «`class_name` для всех не-autoload». Скиллы используют `class_name` повсеместно. Моя претензия про «смешивание презентации и данных» — это чужая эстетика, не стандарт Godot 4.x.

3. **«Premature refactoring» — серьёзное обвинение, и его надо обосновывать конкретным tech-debt-cost.** Не «90 строк — это норм», а «90 строк, и вот эти 6 строк — это боль, которую рефакторинг уберёт». Без этого «premature» превращается в «мне так привычнее».

4. **Known Issue из README — это не варнинг, это задача.** Когда README явно описывает проблему и даёт инструкцию, это задача, а не «дойдёт до Quality-of-Life».

5. **Скиллы `.agents/skills/` — это контракт, а не совет.** Когда `godot-resource-data-patterns` говорит «NEVER use untyped arrays in Resources» — это не рекомендация, это запрет. `parameters: Dictionary` в CombatArena — это нарушение.

6. **Само-коррекция должна быть видимой.** Скрывать, что я ошибся в исходной оценке, было бы нечестно. Этот раздел — не самоуничижение, а зафиксированный learning: «вот как я ошибочно отверг X, и вот почему Y оказался прав».
