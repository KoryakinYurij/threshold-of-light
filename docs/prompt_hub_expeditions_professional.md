# Профессиональный промт для AI-агента: хаб и экспедиции

## Назначение

Этот промт предназначен для AI-агента разработки, который создаёт оригинальную 2D-игру: постоянный однокрановый хаб, из которого игрок отправляется в короткие экспедиции, сражается, принимает рискованные решения, добывает ресурсы и возвращается для развития хаба.

Игра должна быть самостоятельной. Нельзя копировать Tower Wizard, его название, сущности, тексты, интерфейс, визуальные решения, музыку, звуки или ассеты.

# ПРОМТ ДЛЯ АГЕНТА

Ты — senior game director, gameplay programmer, technical designer, UI/UX designer, QA engineer и producer. Разрабатывай игру как профессиональный indie-проект: сначала доказательство fun, затем расширение, затем полировка. Не создавай огромную систему до проверки базового игрового цикла.

## 1. Продуктовая идея

Рабочее название: **Threshold of Light / Порог Света**.

Жанр: 2D hub-builder + короткий action-roguelite + extraction-lite + лёгкая incremental-прогрессия.

Игрок управляет живым маяком на границе тёмного мира. Маяк развивается на одном экране. Из него игрок отправляет разведчика в малые процедурные экспедиции, где добывает материалы, артефакты и воспоминания. В экспедиции можно продолжать путь ради более сильной награды или эвакуироваться. После возвращения добыча используется для строительства и перестройки хаба.

Главная идея:

> Хаб не просто даёт бонусы к следующей экспедиции. Его модули меняют правила самой экспедиции, а экспедиции физически и функционально меняют хаб.

## 2. Обязательные ограничения

- Первая версия — 2D.
- Главный экран хаба — один постоянный экран.
- Не создавать большой open world.
- Экспедиция — маленькая карта из связанных узлов или компактных комнат.
- Один забег MVP длится 5–12 минут.
- Бой должен быть компактным и понятным.
- Не создавать более 4 ресурсов в MVP.
- Не добавлять prestige только ради множителя.
- Не добавлять новую валюту, если она не создаёт новое решение.
- Не добавлять процедурную генерацию ради бесконечного контента.
- Все данные предметов, врагов, модулей, событий и наград должны быть data-driven.
- Сначала реализовать greybox с простыми формами, потом арт.

## 3. Выбор технологии

Используй Godot 4.x и GDScript, если в рабочем окружении уже не задан другой движок.

Перед реализацией:

1. Проверь доступную версию Godot.
2. Проверь экспорт на Windows и, если требуется, Web.
3. Проверь совместимость сторонних плагинов.
4. Не подключай плагин без проверки лицензии, актуальности и необходимости.
5. Для MVP предпочитай собственную простую реализацию, если плагин увеличивает риск зависимости.

Используй:

- сцены для визуально составных объектов;
- Custom Resources для конфигурации модулей, врагов, предметов и событий;
- typed GDScript;
- сигналы для связи систем;
- отдельную модель состояния игры;
- фиксированный simulation tick для экономики;
- physics tick для движения и столкновений;
- seed для воспроизводимых экспедиций;
- object pooling только после профилирования.

## 4. Профессиональные эталонные решения

Изучи и используй как референсы, но не копируй код, ассеты или структуру без необходимости:

- воспроизводимых turn/action циклов, если MVP окажется лучше в пошаговом формате.

Не подключай LimboAI автоматически. Для трёх простых врагов начни с собственного typed FSM. Подключай behavior tree только после доказательства, что FSM становится ограничением.

### Процедурные карты

- Godot 4 procedural generation demos от GDQuest: https://github.com/gdquest-demos/godot-4-procedural-generation

Для MVP используй не полностью случайные карты, а **контролируемый граф узлов**:

- 7 узлов;
- старт;
- 2–3 обычных события;
- ресурсный узел;

Сначала реализуй набор авторских шаблонов с перемешиванием параметров. Полноценную процедурную генерацию подключай только после теста повторяемости и fairness.

### Инвентарь и предметы

- Modular inventory system for Godot 4: https://github.com/expressobits/inventory-system
- Godot Open RPG от GDQuest: https://github.com/gdquest-demos/godot-open-rpg

Для MVP не создавай сложную сетку инвентаря. Используй ограниченный список слотов:

- 1 оружие;
- 2 активные способности;
- 3 временных модификатора;
- 1 слот нестабильной добычи;
- 1 слот закреплённой добычи.

## 5. Два режима и их граница

### Хаб

Темп: спокойный. Игрок наблюдает, строит, перестраивает, запускает экспедицию.

### Экспедиция

Темп: активный. Игрок двигается, сражается, выбирает маршрут, собирает добычу и решает, продолжать ли путь.

Не смешивай бесконечный idle-доход с активным боем. Idle должен развивать хаб и подготовку, а не автоматически выигрывать экспедиции.

## 6. Хаб на одном экране

Создай постоянный экран с центральным Маяком и модульными гнёздами вокруг него.

### MVP-модули

1. **Сердце Маяка**
   - стартовая точка;
   - энергия;
   - запуск экспедиции;
   - базовый passive income.

2. **Карта Трещин**
   - выбор маршрута;
   - отображение риска;
   - отображение возможных типов наград;
   - выбор seed/экспедиционного профиля.

3. **Кузница Формы**
   - выбор оружия;
   - создание стартового билда;
   - изменение одной механики атаки.

4. **Сад Памяти**
   - переработка добытых воспоминаний;
   - временные и постоянные эффекты;
   - открытие новых модификаторов.

5. **Мастерская**
   - постоянные улучшения;
   - дополнительные слоты;
   - улучшение эвакуации;
   - автоматизация скучных хабовых действий.

Каждый модуль должен:

- иметь 3 уровня в MVP;
- визуально меняться после улучшения;
- влиять хотя бы на одно конкретное правило экспедиции;
- иметь стоимость и понятную отдачу;
- занимать место или потреблять энергию;
- иметь минимум один компромисс.

## 7. Пространственная система хаба

Хаб должен быть не меню, а пространственной системой.

Реализуй:

- ограниченные гнёзда вокруг Маяка;
- drag-and-drop или выбор позиции;
- соседские синергии;
- preview эффекта при размещении;
- возможность безопасно перестроить модуль;
- частичный возврат ресурсов при демонтаже;
- визуальное изменение проводников энергии и света.

Примеры:

- Кузница рядом с Сердцем повышает силу стартового оружия, но занимает место для Сада.
- Сад рядом с Картой увеличивает шанс ресурсных узлов.
- Мастерская рядом с Причалом уменьшает потерю нестабильной добычи.

Не допускай одной очевидной оптимальной раскладки. Минимум две стратегии должны быть конкурентоспособны.

## 8. Экспедиционный цикл

### Запуск

Перед стартом показать:

- доступный маршрут;
- ожидаемый тип угроз;
- диапазон награды;
- риск потери;
- стартовое оружие;
- активные модули хаба;
- прогноз времени забега.

### Структура маршрута

MVP: 7 узлов, из которых игрок каждый раз видит 2–3 следующих варианта.

Типы узлов:

- бой;
- ресурс;
- торговец/обмен;
- событие;
- элита;
- безопасный лагерь;
- эвакуация;
- страж.

Каждый узел обязан давать выбор или риск, а не только «нажать кнопку и получить число».

### Завершение

Экспедиция заканчивается одним из трёх способов:

1. успешная эвакуация;
2. поражение;
3. победа над финальным стражем.

## 9. Риск и эвакуация

Раздели награды на:

- **закреплённые** — сохраняются при поражении;
- **нестабильные** — теряются при поражении;
- **открытия** — новые знания, которые сохраняются частично или полностью.

Игрок должен иметь возможность эвакуироваться после безопасного узла.

Чем глубже маршрут:

- выше множитель награды;
- сложнее враги;
- выше шанс элиты;
- больше нестабильной добычи;
- сильнее эффекты событий.

Перед каждым рискованным выбором показывай:

- возможную награду;
- вероятность угрозы, если она известна;
- что игрок теряет при смерти;
- ближайшую точку эвакуации.

Нельзя наказывать игрока непрозрачной случайностью.

## 10. Боевая система MVP

Используй компактный top-down action combat:

- свободное движение;
- базовая атака с cooldown;
- одна активная способность;
- одно уклонение или защитное действие;
- 3 типа врагов;
- телеграфируемые атаки;
- короткие арены;
- понятные hitbox/hurtbox;
- pause в меню;
- визуальный и звуковой feedback.

### Враги MVP

1. **Преследователь**
   - идёт к игроку;
   - простая атака в ближнем бою.

2. **Пульсатор**
   - держит дистанцию;
   - заряжает телеграфируемый дальний удар.

3. **Собиратель**
   - пытается украсть или испортить нестабильную добычу;
   - заставляет выбирать цель.

Каждый враг должен быть читаемым по силуэту, цвету, анимации и звуку. Цвет не должен быть единственным способом различения.

### Состояния врага

Минимум:

```text
IDLE → SEEK → TELEGRAPH → ATTACK → RECOVER
                 ↓
              STUN / HURT → DEAD
```

Используй отдельные FSM для:

- движения;
- атак;
- особых реакций.

Не превращай `HURT` в глобальное состояние, если это просто обработка урона и анимация.

## 11. Временные билды

После боя или события игрок выбирает один из 3 вариантов.

Модификатор обязан менять стиль игры. Не ограничивайся `+10% damage`.

Примеры:

- атака оставляет световую дорожку, но снижает скорость;
- уклонение телепортирует к ближайшему ресурсу;
- каждый третий критический удар создаёт приманку;
- потеря здоровья повышает добычу;
- сбор нестабильной добычи повышает урон, но ускоряет появление элиты;
- оружие пробивает врагов насквозь, но имеет короткую дальность;
- успешная эвакуация усиливает следующий забег, смерть стирает эффект.

В MVP создать 10–12 модификаторов, распределённых по 3 архетипам:

- мобильность;
- риск/награда;
- контроль поля.

## 12. Постоянная прогрессия

Используй три слоя:

### Добыча

Тратится на модули и улучшения хаба. Часть можно потерять.

### Знание мира

Сохраняется всегда. Открывает:

- новые модули;
- новые маршруты;
- новые враги;
- новые типы событий;
- новые варианты наград.

### Перенастройка

Игрок может разобрать модуль и построить другой. Возвращается часть материалов. Нет обязательного полного сброса.

Если понадобится prestige, реализуй его только как отдельный добровольный режим:

- он открывает новое правило, а не только множитель;
- заранее показывает награду;
- сохраняет фундаментальные открытия;
- автоматически ускоряет скучные ранние действия;
- допускает разные стили забегов.

## 13. Ресурсы MVP

Ограничься четырьмя:

1. **Свет** — пассивно производится в хабе, питает модули.
2. **Материалы** — добываются в экспедициях, строят модули.
3. **Воспоминания** — открывают новые правила и модификаторы.
4. **Нестабильная добыча** — рискованный ресурс с высокой ценностью.

Для каждого ресурса определить:

- источник;
- потребители;
- предел/soft cap;
- визуальный feedback;
- поведение при смерти;
- offline progress, если применимо.

Не используй огромные числа в MVP. Числа должны оставаться читаемыми.

## 14. Сохранения

Раздели:

- `settings` — звук, управление, accessibility;
- `profile` — открытия мира;
- `hub_state` — модули, уровни, расположение;
- `run_state` — только если разрешено сохранение в экспедиции.

Для MVP запрещай сохранение во время боя. Разрешай сохранение:

- в хабе;
- на безопасной точке;
- после завершения узла.

Сохраняй только данные, необходимые для восстановления состояния. Не сохраняй Node-ссылки.

Требования:

- `user://`;
- атомарная запись через временный файл и замену;
- версия формата;
- миграции;
- backup save;
- 3 слота;
- импорт/экспорт для отладки;
- обработка повреждённого файла;
- отдельное сохранение настроек;
- тесты смерти, эвакуации и перезапуска.

JSON допустим для читаемого прототипа, бинарная сериализация — для сложных runtime-типов. Выбери один формат, обоснуй выбор и не смешивай форматы без необходимости.

### Правила архитектуры

- UI не изменяет ресурсы напрямую.
- Системы не ищут узлы через `get_node()` в циклах.
- Используй группы и кэшированные ссылки.
- Не создавай «God object» с логикой всего проекта.

- Runtime-объекты имеют стабильные ID.
- Сигналы подключаются в коде и документируются.
- Каждая система имеет публичные команды и события.

## 17. Порядок реализации

### Фаза 0 — исследование проекта

Перед кодом:

1. перечисли существующие инструменты и их лицензии;
2. проверь версии репозиториев;
3. выпиши, какие части можно использовать как референсы;
4. исключи неактуальные, незаконченные или слишком тяжёлые зависимости;
5. предложи собственный минимальный вариант.

### Фаза 1 — greybox

Создай:

- один хаб;
- один модуль;
- кнопку запуска экспедиции;
- 7 узлов;
- игрока;
- одного врага;
- одну награду;
- эвакуацию;
- возврат в хаб.

Критерий: игрок может пройти полный цикл без placeholder-меню и без ручного редактирования состояния.

### Фаза 2 — системный vertical slice

Добавь:

- четыре модуля;
- три врага;
- три типа узлов;
- рискованную добычу;
- 6 модификаторов;
- сохранение;
- базовые звуки и feedback.

### Фаза 3 — balance slice

Добавь:

- два жизнеспособных билда;
- 10–12 модификаторов;
- безопасную точку;
- элиту;
- один финальный страж;
- 12 постоянных открытий.

### Фаза 4 — полировка

Только после playtest:

- арт;
- частицы;
- анимации;
- музыка;
- accessibility;
- настройки;
- onboarding;
- оптимизация;
- экспорт.

## 18. Playtest-гипотезы

Проверь:

1. Игрок понимает, как начать экспедицию за 30 секунд.
2. Игрок видит связь между модулем хаба и правилом экспедиции.
3. Игрок хотя бы раз выбирает эвакуацию вместо максимального риска.
4. После смерти игрок знает, что сохранилось.
5. Возвращение в хаб вызывает желание что-то построить.
6. Две стратегии действительно отличаются.
7. Игрок не обязан вручную покупать десятки ранних улучшений.

Записывай только обезличенные debug-метрики:

- время до первой экспедиции;
- длина забега;
- глубина маршрута;
- доля эвакуаций;
- причина смерти;
- выбранные модули;
- время от возвращения до нового запуска.

## 19. Формат работы агента

Перед кодом выдай:

1. краткое дизайнерское резюме;
2. список допущений;
3. таблицу систем и их приоритетов;
4. архитектуру;
5. дерево файлов;
6. список зависимостей и лицензий;
7. план первой фазы;
8. критерии «готово» для первой фазы.

После каждой фазы:

- запусти проект;
- выполни тесты;
- исправь ошибки до добавления новых систем;
- перечисли изменённые файлы;
- покажи, как запустить проект;
- опиши известные ограничения;
- не выдавай псевдокод вместо работающего кода.

Если решение неоднозначно:

- предложи два варианта;
- сравни стоимость, риск и расширяемость;
- выбери один для MVP;
- не добавляй сложность без подтверждения.

Главный приоритет:

```text
fun первого полного цикла
> понятность риска
> стабильность сохранений
> расширяемость архитектуры
> количество контента
> визуальная полировка
```

## 20. Финальная проверка перед выдачей MVP

Ответь «да/нет» на каждый пункт:

- Есть ли полный цикл хаб → экспедиция → бой → добыча → эвакуация → хаб?
- Может ли игрок понять риск до выбора?
- Меняет ли каждый модуль хаба конкретное правило экспедиции?
- Сохраняется ли важный прогресс после смерти?
- Есть ли два разных жизнеспособных билда?
- Не является ли главный выбор простым сравнением множителей?
- Можно ли воспроизвести экспедицию по seed?
- Не зависит ли экономика от FPS?
- Есть ли тесты на смерть и эвакуацию?
- Работает ли проект после перезапуска?
- Доступны ли основные действия с клавиатуры?
- Не копирует ли проект защищённые элементы чужой игры?

Если хотя бы на один ключевой вопрос ответ «нет», сначала исправь проблему, а не добавляй новый контент.

- Microsoft Xbox Accessibility Guidelines рекомендуют несколько каналов обратной связи, ясную навигацию, переназначаемый ввод, контраст, субтитры и настройки движения: https://learn.microsoft.com/en-us/gaming/accessibility/guidelines

# Ревизия документа после повторной проверки источников

## Статус документа

Этот документ следует считать **production-oriented MVP specification**, но не готовым production framework. Перечисленные репозитории — это смесь официальных демо, учебных примеров и потенциальных зависимостей. Ни один репозиторий нельзя подключать автоматически только потому, что он опубликован на GitHub.

Проверять нужно:

- актуальный tag или commit;
- версию Godot;
- LICENSE и лицензии вложенных ассетов;
- экспорт на целевые платформы;
- наличие тестов;
- активность поддержки;
- размер и сложность зависимости;
- возможность удалить её без переписывания игры.

## Зафиксированная техническая база

Используй конкретную версию Godot, выбранную до начала разработки. Для текущего прототипа зафиксируй:

```text
Engine: Godot 4.6.stable
Language: GDScript 2.0
Renderer: Compatibility для Web/широкой совместимости; Forward+ только при подтверждённой необходимости
Targets: Windows first; Web only after core slice is stable
```

Если в окружении доступна другая stable-версия, агент обязан сначала проверить migration notes и изменить эту строку явно. Не использовать расплывчатое `Godot 4.x`.

Версии сторонних компонентов фиксировать commit SHA или release tag, а не ветку `main`.

## Уточнённое разделение данных и объектов

Godot определяет `Node` как объект поведения/сцены, а `Resource` как контейнер данных. Применяй это разделение так:

### Custom Resources — статические определения

```text
ModuleDefinition
EnemyDefinition
WeaponDefinition
AbilityDefinition
ModifierDefinition
EncounterDefinition
LootTable
RouteTemplate
```

Они лежат в `res://data/`, редактируются в Inspector и не содержат runtime-состояние текущего забега.

### Nodes — runtime-представление

```text
Player
Enemy
Projectile
Pickup
ExpeditionMap
HubModuleView
CombatArena
UI panels
```

### Plain state objects — сохраняемое состояние

```text
ProfileState
HubState
RunState
SettingsState
SaveEnvelope
```

Нельзя сохранять ссылки на Node, Callable, Signal или случайный NodePath как источник истины. При загрузке сначала создавай состояние, затем реконструируй Nodes из стабильных ID.

## Уточнённый combat contract

Для MVP зафиксировать:

```text
Perspective: top-down 2D
Movement: WASD / left stick, 8 directions
Aim: mouse position / right stick
Basic attack: manually aimed projectile
Ability: one cooldown ability
Defense: short dash with invulnerability frames
Collision: Area2D hitbox/hurtbox, not full rigid-body combat
Simulation: physics tick
Pause: allowed outside active attack resolution
Enemy AI: own typed FSM for MVP
```

Минимальные компоненты:

```text
HealthComponent
DamageReceiver
Hitbox
Hurtbox
CooldownComponent
StatusEffectController
MovementController
CombatController
EnemyBrain
```

Разделяй movement FSM и combat ability FSM. `Hurt` не обязан быть глобальным состоянием: если это только уменьшение здоровья и animation feedback, это должен делать Health/Damage layer.

## Уточнённая архитектура сигналов

Следуй правилу:

```text
call down, signal up
```

Метод родителя или контроллера запускает действие ребёнка. Ребёнок emits signal о результате. Не использовать EventBus для каждой мелочи.

Использовать EventBus/autoload только для действительно дальних событий:

```text
run_started
run_resolved
resource_changed
hub_changed
save_completed
```

Локальные события подключать напрямую. Сигнал должен называться событием в прошедшем времени: `item_collected`, `enemy_defeated`, `module_built`.

## Production SaveManager

Реализовать такой pipeline:

```text
1. Собрать typed state в SaveEnvelope.
2. Проверить обязательные поля и version.
3. Сериализовать только разрешённые primitive/array/dictionary значения.
4. Записать в user://save_1.tmp.
5. Закрыть файл и проверить размер/чтение.
6. Переименовать старый save_1 в save_1.bak.
7. Переименовать tmp в save_1.
8. При ошибке загрузки использовать backup.
9. Прогнать migration до текущей version.
10. Восстановить Nodes только после успешной валидации.
```

Настройки хранить отдельно через `ConfigFile`. JSON удобен для debug, но Vector2, Resource и другие типы должны конвертироваться вручную. Если нужен бинарный формат, использовать только контролируемый dictionary и проверять структуру после чтения.

## One-screen UI contract

При базовом разрешении 1280x720:

- не менее 90% хаба видно одновременно;
- постоянная верхняя область показывает только 4 ресурса и текущую цель;
- панель выбранного модуля открывается сбоку или как overlay;
- overlay не скрывает Сердце Маяка без необходимости;
- запуск экспедиции занимает не более двух действий;
- важное действие доступно мышью, клавиатурой и gamepad;
- UI не сообщает состояние только цветом;
- масштаб UI, контраст и reduced motion входят в MVP;
- все destructive actions имеют confirmation.

## Incremental boundary

Incremental-часть должна оставаться в хабе:

- Свет производится пассивно;
- Материалы обрабатываются в фоне;
- исследование может идти по времени;
- хаб получает ограниченный offline progress;
- бой и выбор маршрута никогда не проходят автоматически;
- автоматизируются скучные покупки и повторяемая обработка, но не meaningful decisions.

Не вводить экспоненциальные числа и престиж в MVP. Сначала проверить риск, эвакуацию и связь построек с экспедициями.

## Controlled procedural generation

MVP использует не свободную генерацию dungeon, а валидируемый граф:

```text
Start
 ├── Combat
 │    ├── Resource
 │    └── Event
 ├── Combat
 │    └── Safe Camp
 └── Risk / Elite
      └── Extraction or Guardian
```

Генератор обязан проверять:

- существует ли путь Start → Extraction;
- есть ли максимум два последовательных combat nodes;
- есть ли safe point до финального риска;
- награды не появляются только в недостижимых узлах;
- seed воспроизводит тот же граф;
- минимальная и максимальная длина находятся в заданном диапазоне;
- первые два узла не требуют высокой силы билда.

Добавить property-based или хотя бы batch tests: сгенерировать 10 000 seed и проверить инварианты графа.

## CI и контроль качества

Добавить в проект:

```text
.gitignore
.gitattributes
README.md
CHANGELOG.md
LICENSES.md
export_presets.cfg
```

CI должен:

1. установить зафиксированную версию Godot;
2. запустить проект headless;
3. выполнить unit/integration tests;
4. выполнить gdformat check;
5. выполнить gdlint;
6. проверить отсутствие parse errors;
7. собрать Windows debug build;
8. собрать Web только после подтверждения Web compatibility.

Профилирование проводить после появления измеримой проблемы. Не добавлять pooling, multithreading, сложный EventBus или GDExtension «на всякий случай».

## Playtest decision thresholds

Используй не только сбор метрик, но и заранее заданные действия:

| Наблюдение | Вероятная проблема | Действие |
|---|---|---|
| Более 30 секунд до понимания запуска | слабая onboarding-цепочка | убрать меню, добавить visual affordance |
| Меньше 20% используют эвакуацию | риск/награда нечитабельны или эвакуация неценна | показать loss preview, усилить safe reward |
| Более 40% не видят связь модуля и экспедиции | хаб не влияет на run | добавить немедленное preview и визуальную связь |
| Более 50% умирают до первой safe point | слишком высокий ранний риск | снизить угрозу или гарантировать escape |
| Повторный запуск занимает более 90 секунд | слишком много chores | добавить automation и быстрый старт |
| Всегда выбирается один модуль | нет meaningful trade-off | ослабить dominant option или усилить альтернативу |

Эти пороги не являются универсальными законами. Они стартовые гипотезы для playtest и должны изменяться по фактическим данным.

## Обновлённый definition of done для MVP

- полный цикл хаб → экспедиция → бой → добыча → эвакуация → хаб;
- minimum two viable builds;
- минимум два жизнеспособных маршрута;
- гарантированный достижимый escape path;
- seed reproducibility;
- 10 000 генераций проходят graph invariants;
- смерть сохраняет профиль и теряет только заявленное;
- сохранение переживает повреждённый основной файл через backup;
- migration test с version 0 → current;
- headless test проходит;
- debug Windows export запускается;
- действия доступны keyboard/gamepad;
- state не зависит от FPS;
- нет обязательной внешней зависимости для базового core loop;
- лицензии всех включённых компонентов записаны в `LICENSES.md`.
